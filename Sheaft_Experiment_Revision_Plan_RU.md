# Sheaft: план корректировки экспериментов

Версия 2.1, 27 сентября 2026 года. Статус: проект протокола следующей кампании. Добавлен отдельный эксперимент построения расписания для сопоставления с опубликованным показателем BFG APS (раздел 17). Новые результаты по этому протоколу ещё не получены.

Основание: публичный репозиторий a-a-k/sheaft-tsfg-experiments, снимок 0ff8dafe10331aa574b23a32ef611f3a6502a909; завершённая кампания 26–27 сентября; приложенный аналитический отчёт TSFG по задаче Ozon/МБ3РЛаб. Ссылки на первичные материалы приведены в конце документа.

## 1. Цель и границы корректировки

Проверить исполнение выбранного производственного плана при остановках оборудования, задержках операций и дефиците общих ресурсов. Установить, какие ограничения вызвали срыв, где накопились детали и какое заранее определённое изменение улучшило результат. Масштабирование до миллиона операций остаётся отдельной проверкой производительности.

Предыдущая кампания проверила пооперационную модель на фиксированных назначениях и очередях. TSFG совпал с эталонами на проверенных данных и уступил специализированным DES/DAG по времени. Расширения с конечными буферами и дополнительным ресурсом прошли малые проверки. Основные большие замеры этих расширений не охватили.

Следующая кампания должна ответить на четыре самостоятельных вопроса:

1. Совпадают ли результаты TSFG и независимого событийного расчёта при совместном действии конечных буферов и общих ресурсов?
2. Какова стоимость точного расчёта этой постановки на 100 тысячах и миллионе операций?
3. Дают ли рекомендации по резервам измеримый эффект на новых сценариях?
4. В каких пределах допустима потоковая агрегация исходного TSFG?

Отрицательные результаты первой кампании сохраняются. Добавление ограничений обусловлено исходным промышленным сценарием. Область сравнения фиксируется до измерений; ограничения нельзя подбирать по тому, какой движок на них выиграл.

Все сборки, тесты, генерация входов, повторный анализ числовых данных, измерения и выпуск отчётов выполнять исключительно на GitHub-hosted GitHub Actions. Локально допустимы чтение материалов, редактирование кода и документов, операции Git и получение готовых артефактов. Этот документ подготовлен без новых запусков моделирования.

### Реестр происхождения

В первом новом workflow создать evidence-v2.json. Для каждой записи сохранить: старый run_id, commit, идентификатор и SHA-256 артефакта, хеш входа и сценариев, профиль семантики, версию движка, режим остановки, состав выхода, статус проверки, причину повторного использования. Проверить фактическую доступность Actions-артефактов и release-архива.

Присваивать один из статусов: REUSED_UNCHANGED, DERIVED_FROM_SAVED_OUTPUT, RERUN_REQUIRED, MISSING_ARTIFACT, NOT_APPLICABLE. Недоступный файл нельзя считать восстановленным по сводной таблице. При необходимости выполнить адресный повтор утраченной серии и связать новый результат со старым; старую запись не заменять.

В большой E2 после измерений сохранялись хеши полных строк, а большинство самих трасс удаляли. По хешу нельзя восстановить сроки операций, очереди или результат при другом сроке миссии. Повторный анализ таких показателей требует сохранённых полей либо повторного моделирования конкретных сценариев.

## 3. Первый этап: повторный анализ без запусков движков

Создать workflow reuse_analysis_v2.yml. В нём использовать только завершённые артефакты.

### 3.1. Исправить область утверждений

Сохранить прежние H1–H5 и результаты. Добавить таблицу поддерживаемых ограничений и название реализации в каждую таблицу времени. Результаты первой кампании не переклассифицировать в подтверждение новых гипотез.

DAG-REF и DES-REF написаны внутри этого исследования. Их код опубликован. Они не представляют производительность коммерческих BFG или PlantTwin. Для DAG-REF явно указать применимость к текущему профилю фиксированных очередей. Ограничения этой реализации не следует распространять на все возможные графовые алгоритмы.

### 3.2. Повторно оценить E4 по выпуску

В engines/reserve_main.cpp сохранены outcomes, produced_jobs и cmax_scaled_ticks для семи конфигураций каждого сценария. Проверить наличие этих полей в evaluation-independent.json и evaluation-common-cause.json.

Для каждого вмешательства рассчитать парную разность числа завершённых заказов к исходному D. Представить среднее, медиану, долю сценариев с улучшением и ухудшением, парный интервал неопределённости. Целую сценарную запись со всеми конфигурациями сохранять единицей повторной выборки.

В F2 нулевая доля полностью выполненных заданий могла сопровождаться различиями в числе готовых заказов. В F1 можно сопоставить сохранённые полные сроки, если все соответствующие записи содержат известный Cmax. При нулевом эффекте сохранить нулевой результат.

Для незавершённых миссий Cmax в E4 записан как null. По этим данным нельзя вычислить полное опоздание, средний срок или 95-й процентиль завершения. Запрещено подставлять D вместо неизвестного срока. Исходные значения Cmax записаны в масштабе времени ×11; восстановить единицы до сравнения.

Этот анализ выполняется после просмотра исходных результатов. Обозначить его как дополнительный исследовательский анализ. Прежняя H5 остаётся неподтверждённой. Нулевой выборочный эффект и вырожденный bootstrap-интервал не доказывают нулевой эффект во всей совокупности сценариев.

### 3.3. Сохранить анализ ошибок G2

Использовать существующие DIAGNOSTIC-результаты и таблицу строгих сроков. Свести ошибки по семейству, плотности, размеру и типу ограничения. Отдельно показать ложный прогноз выполнения задания. Совпадение выпуска в благоприятном сценарии не заменяет проверку очередей, НЗП и миссии.

Не запускать старую G2 повторно ради уже известных отрицательных результатов. Новые выводы о промежуточном сроке разрешены только для показателей, которые действительно восстановимы из сохранённой траектории. Из одного Cmax нельзя восстановить НЗП или очередь в произвольный момент.

Выход этапа: REUSE_REPORT_V2_RU.md, evidence-v2.json, e4-output-reanalysis.csv, таблица оставшихся пробелов. Число новых запусков движков на этом этапе равно нулю.

## 4. Разделение постановок и эталонов

| Профиль | Содержание | Основное сравнение |
|---|---|---|
| P0 | Прежние фиксированные назначения и очереди; неограниченные буферы | Прежние TSFG, DES-REF и DAG-REF; результаты сохранить |
| PB | P0 с конечными буферами и блокировкой станка после обработки | TSFG-EXT и новый независимый DES-EXT |
| PR | P0 с общими ресурсами ограниченной ёмкости и их отказами | TSFG-EXT и DES-EXT |
| PBR | Совместное действие конечных буферов и общих ресурсов | Основной новый промышленный профиль: TSFG-EXT и DES-EXT |
| PA | Заранее подготовленный альтернативный план или резервная конфигурация | Тот же применимый точный движок для всех вариантов |
| PF | Потоковая модель в пределах условий допустимой агрегации | Отдельная исследовательская серия с собственным эталоном и допуском |

DAG-REF остаётся в P0. Для PB/PR/PBR текущая реализация получает NOT_APPLICABLE. Поддержка нового ограничения требует отдельной реализации и проверки. При появлении корректного специализированного алгоритма включить его в сравнение по тем же правилам; исключать сильный эталон из-за высокой скорости запрещено.

DES-EXT реализовать в C++ рядом с DES-REF. Сохранить независимую логику переходов относительно Go-адаптера TSFG. Разрешить общий формат входа, спецификацию выходных полей и внешние проверки инвариантов. Копирование одной функции перехода между двумя движками лишит сравнение независимости.

Существующий references/extended_ref.py с рациональным временем Fraction использовать для малых эталонных случаев. SimPy при необходимости добавить как проверку порядка событий и владения ресурсами на небольшой выборке. Самостоятельный перенос всей большой кампании на Python не требуется. Сравнение Go/C++ характеризует конкретные реализации; для утверждения о преимуществе математического метода понадобятся дополнительные контролируемые сравнения.

Для нескольких пулов и ёмкости больше единицы расширить рациональный эталон отдельной реализацией учёта владельцев. Его текущая версия поддерживает один дополнительный ресурс ёмкости 1. Новые возможности допускать ручными случаями с заранее вычисленными ответами, затем сравнивать с DES-EXT и TSFG-EXT. Старые свидетельства E1X относятся только к прежним возможностям эталона.

## 5. Семантика расширенного исполнения

Сохранить уже определённые правила docs/EXTENDED_SPEC_RU.md, кроме явно перечисленных изменений формата. Каждое изменение получает версию и регрессионный пример.

1. Каждая деталь и операция сохраняет индивидуальный идентификатор. Готовность предшественника, начало обработки и освобождение станка имеют разные поля.
2. После обработки деталь удерживает станок до передачи следующей операции. Входной буфер содержит только ожидающие детали; обрабатываемая деталь занимает станок.
3. На общей временной границе сначала зафиксировать завершения, затем изменения доступности, затем выполнить передачи и старты до устойчивого состояния. Установить общий полный порядок разрешения конфликтов: planned_start, job_id, operation_id, machine_id.
4. Основные очереди фиксированы; обгон запрещён. Заранее запланированное начало остаётся нижней границей старта. Проверку политики с обгоном или динамическим выбором станка оформить отдельным профилем.
5. Ресурсы захватывать атомарно вместе со станком при наличии материала. В первом расширении операция требует не более одного общего пула. Зафиксировать размер пула, идентификаторы единиц, правило выбора свободной единицы и календарь недоступности каждой единицы.
6. Сохранять правило E1X: занятый общий ресурс удерживается до завершения обработки, включая остановку станка и собственного ресурса; после обработки освобождается даже при блокировке готовой детали. В документации называть его удерживаемым ресурсом или оснасткой. Применение такого правила к наладчику требует отдельного производственного обоснования.
7. При отказе работа приостанавливается с сохранением остатка. Непрерывное обслуживание на границе отказа трактовать одинаково во всех реализациях. Перенос уже обработанной детали не требует исправности станка, пока отдельный погрузочный ресурс отсутствует в модели.
8. DEADLOCK допустим только при доказанной невозможности дальнейшего продвижения с учётом будущих восстановлений и поступлений. Исчерпание горизонта даёт CENSORED. Незавершённая миссия к D сама по себе взаимную блокировку не доказывает.

В текущем коде buffer_capacity=0 означает неограниченный буфер. Сохранить эту трактовку при чтении старого формата. В новой схеме использовать явное значение unbounded; нулевую вместимость, если она потребуется, определить отдельно. Молчаливое изменение смысла нуля недопустимо.

Основная точная серия использует целочисленные длительности и границы воздействий на общей сетке. Все изменения длительностей округлить при создании сценария по заранее закреплённому правилу, затем передать одинаковые числа обоим движкам. Дробные скорости и независимый подбор шага относятся к отдельному приближённому профилю E1X. Допуск на время не должен менять классификацию выполнения к D.

## 6. Второй этап: совместная корректность на Mk01

Сохранить исходный Mk01 и все базовые планы E1X. Последовательные планы, которыми в E1X заменяли заблокированные исходные планы, пригодны для регрессии. Их недостаточно для доказательства производительности на загруженном производстве.

Новый DES-EXT должен воспроизвести сохранённые 481 сценарий для каждой вместимости 1/2/4 и 15 сценариев общего ресурса. Оптимизированный TSFG-EXT прогнать по тем же затронутым случаям. Сборку неизменного S1 и свидетельство исходных регрессий переиспользовать при совпадении закреплённой среды.

Добавить 135 комбинированных сценариев: три вместимости × пять моментов воздействия × три длительности × три комбинации. Моменты: 10/30/50/70/90% C0; длительности: 5/10/20% C0. C0 относится к конкретному базовому плану расширенного профиля.

Комбинации:

- одновременная остановка заранее выбранного станка и недоступность общего ресурса;
- остановка станка и сдвинутая на половину длительности недоступность ресурса;
- остановка станка, недоступность ресурса и увеличение работы заранее выбранной операции на 50%.

Выбрать станок, ресурс и операцию по фиксированным идентификаторам до запуска; параметры опубликовать в manifest. Границы округлить один раз до общей сетки. Для каждого сценария проверить сроки C0, 1,10C0 и 1,25C0. Получатся 405 проверок миссии на движок сверх прежней регрессии.

Дополнить ручные примеры одновременным освобождением места и ресурса, передачей на тот же станок, временной остановкой с будущим восстановлением и настоящей взаимной блокировкой. Проверять индивидуальные начала, окончание обработки, передачу детали, освобождение станка, интервалы владения ресурсом и остаток работы. Проверка только итогового Cmax недостаточна.

Добавить ручной контроль совместного срыва: две последовательные операции A и B по 10 единиц времени на разных станках, плановые начала 0 и 10, срок D=22. Отказ станка A на [0,2) и отказ станка B на [12,14) по отдельности дают Cmax=22; совместно дают Cmax=24. Это аналитически заданные ожидаемые значения для нового теста. Такой пример проверит случай, когда каждый одиночный отказ допустим, а сочетание нарушило срок.

Критерий допуска: точное совпадение обязательных полей и исходов, отсутствие нарушения вместимости, двойного владельца ресурса, потери материала и нарушения очередности. Первое расхождение останавливает соответствующую новую серию. Старые результаты при этом сохраняют прежний статус.

## 7. Доработка адаптера до масштабирования

В engines/tsfg_op/extended_adapter.go процедура extBoundary перебирает x.order, содержащий все операции, внутри итераций на каждой временной границе. Поэтому механическое увеличение N в существующей E1X создаст дополнительную стоимость полного обхода N на каждом шаге. Этот факт установлен по коду; он не заменяет измерение долей времени.

Для TSFG-EXT-V2 создать индексы готовых голов очередей, деталей, ожидающих передачи, и операций, ожидающих освобождения общего ресурса. После изменения состояния пересматривать связанные элементы. Сохранить общий порядок разрешения конфликтов и обслуживание исходным S1. Число повторных проходов до устойчивого состояния ограничивать доказанным прогрессом, а нарушение ограничения считать ошибкой.

Записывать счётчики: временные шаги S1, посещения операций, посещения станков, попытки передачи, изменения зависимостей, запросы ресурсов, выделения памяти и время подготовки. Замер распределения CPU выполнять отдельным запуском, который не входит в парное сравнение скорости.

Новый алгоритм пропуска времени или изменение исходного S1 в эту обязательную доработку не входят. Если потребуется такой алгоритм, выпустить самостоятельную версию с явной спецификацией. Смена языка также образует новую реализацию. Ни одну из них нельзя переименовать в прежний измеренный TSFG.

После изменения адаптера повторить только затронутую регрессию этапа 6. Прежние цифры ускорения адаптера на 31–32% сохраняются как исторический результат.

## 8. Наборы данных и допустимость исходного плана

Переиспользовать маршруты, длительности, назначения и поступления F1/F2 с seed 101/102/103. Создавать производные экземпляры с parent_dataset_sha256, extension_spec_version и отдельным именем. Старые файлы не перезаписывать.

Первый отбор: N=1 000 и 10 000, DENSE, профили PB/PR/PBR. Получатся 2 семейства × 2 размера × 3 seed × 3 профиля = 36 экземпляров. Буферы 1/2/4 проверить на номинальное исполнение; основной кандидат для измерений PBR использует вместимость 2. Чувствительность к вместимости остаётся отдельной таблицей.

Для масштабируемого общего ресурса задать пул на технологическую группу оборудования. По детерминированному признаку назначить потребность четверти операций. Рассчитать ёмкость пула из суммарной требуемой работы и исходного C0 с целевой средней нагрузкой 0,8; формула c_r=max(1,ceil(W_r/(0,8C0))). Потребность операции относится к группе назначенного станка. Опубликовать фактическую нагрузку, ожидание ресурса и частоту конкуренции. При отсутствии конкуренции классифицировать экземпляр как слабый контроль воздействия данного ограничения.

Это новый синтетический профиль ресурса. Параметр 0,8 задаёт проектную нагрузку; он не считается статистикой предприятия. Старую E1X с одним ресурсом ёмкости 1 сохранить отдельно.

Перед отказами выполнить номинальный сценарий M0. Для каждого экземпляра сохранить результат исходного плана: завершение, взаимную блокировку либо цензурирование. Заведомо неисполняемый план полезен для проверки обнаружения проблем, но не входит в общую таблицу времени нормально завершающихся заданий.

Если новый профиль изменил номинальные начала, создать версию расширенного базового плана по полному номинальному исполнению и проверить её повтором без отказов. Сохранить прежние и новые очереди, времена, C0 и причину изменения. Проверить, что повторное исполнение воспроизвело этот план.

Если фиксированные очереди вызвали DEADLOCK, не заменять план автоматически последовательным расписанием для основной скоростной серии. Поместить экземпляр в серию неисполняемых планов. Для нового допустимого расписания потребуется отдельно закреплённый генератор с ограничениями либо внешний готовый план; выпуск такого входа оформить следующей версией данных. До его появления размер соответствующей основной серии считается неполным.

Перед переходом к большим замерам для каждой заявляемой области должны быть три номинально допустимых экземпляра с заранее фиксированными seed. Если этого нет, сначала устранить пробел генератора. Подбирать seed по выигрышу TSFG запрещено.

## 9. Сценарии нарушений и сроки миссии

Старые сценарии использовать для регрессии и прямого сопоставления совместимых профилей. Для новой подтверждающей серии создать отдельный namespace генератора v2 и новые purpose. Схему получения seed из SHA-256 закрепить буквально, включая число байт и порядок байтов. Старую восьмибайтовую схему v1.1 не менять задним числом.

Банк для проверки скорости содержит 100 новых сценариев на экземпляр:

| Воздействие | Количество |
|---|---:|
| Остановка одного станка | 20 |
| Увеличение длительности одной операции | 20 |
| Недоступность единицы общего ресурса | 20 |
| Два нарушения с разными моментами начала | 20 |
| Общая причина, затрагивающая несколько единиц оборудования и ресурс | 20 |

Идентификаторы выбирать воспроизводимо; моменты распределить по рабочему горизонту. Длительности воздействия брать из заранее фиксированного набора 0,01/0,05/0,20 C0, увеличение работы из 25/50/100%. Если тип ресурса отсутствует, использовать явно отдельную матрицу PB; не превращать отсутствие ресурса в незаметное пустое воздействие.

Для PBR реализовать все пять строк. Синхронные и разнесённые воздействия хранить отдельно. M0 не включать в счётчик K=100. Предварительные K=10 должны быть самостоятельными процессами и иметь отдельные идентификаторы сценариев.

Основной скоростной режим: MISSION с D=1,10C0 конкретного расширенного базового плана. Он сохраняет сопоставимость определения миссии с прежней кампанией. Для диагностики на малых наборах вычислить полные траектории до завершения, доказанного DEADLOCK либо горизонта 10D. Дополнительно проверить исходы для D=C0 и 1,25C0; зафиксировать это до новых запусков.

Прежняя комбинация D=1,10C0 и коротких синхронных остановок часто оставляла бинарный исход неизменным. Разнесённые воздействия и ограничения буферов расширяют проверку. Сохранять величину задержки, число незавершённых заказов, блокировки и ожидание ресурсов даже при одинаковом исходе миссии.

Значение вероятности производственного срыва нельзя оценивать по равномерной сетке искусственных нарушений. Для вероятностного опыта нужен отдельный закон генерации и независимая оценочная выборка.

## 10. Третий этап: измерения с ограничением расходов

### 10.1. Предварительные запуски

На 36 экземплярах этапа 8 выполнить M0 и самостоятельный K=10 для TSFG-EXT-V2 и DES-EXT. Лимит процесса 60 секунд, 1 CPU, 4 GiB. K=10 содержит по два сценария каждого вида для PBR; остальные профили получают собственный закреплённый состав.

Для PR использовать тот же состав пяти видов. Для PB задать четыре одиночные остановки станка, два увеличения работы, две пары разнесённых остановок и две общие причины, затрагивающие только станки. Номинальные проверки вместимостей 1/2/4 относятся к подготовке входов; в 36 экземпляров предварительного измерения входит выбранная основная вместимость 2.

Задача этапа: допустить корректность больших данных, проверить фактическое участие ограничений и оценить стоимость следующего этапа. Единичные предварительные измерения не подтверждают двукратное ускорение. Для каждого отказа допуска сохранять причину: ошибка, неисполняемый исходный план, нехватка памяти, таймаут или отсутствие значимого воздействия ограничения.

### 10.2. Основная новая серия

Начать с PBR, N=100 000, F1/F2, трёх seed. PB и PR остаются контрольными сериями, раскрывающими вклад отдельных ограничений. Их полное масштабирование не требуется для первого результата PBR.

На каждый экземпляр выделить три независимые GitHub-hosted VM. На одной VM выполнить два самостоятельных процесса каждого движка в порядке ABBA; порядок чередовать между VM по заранее заданному правилу. Внутри VM движки не должны конкурировать за CPU. Для каждого процесса K=100 и предел 300 секунд.

Полная серия содержит 2 семейства × 3 seed × 3 VM × 4 процесса = 72 измеряемых процесса. Предельное время этих процессов составляет 6 CPU-часов, без подготовки, проверки и хранения результатов.

До миллионной основной серии выполнить самостоятельный K=10 на миллионе операций для всех трёх seed каждого семейства. Переход к K=100 допускается, если оба движка завершили все соответствующие K=10 корректно и каждый процесс уложился в 25 секунд. Это правило ограничивает бюджет; оно не гарантирует завершение K=100. Все не прошедшие переход случаи и времена сохранить.

Миллионная серия, если допущена полностью, добавит ещё 72 процесса и максимум 6 CPU-часов измерений. Если переход не пройден, опубликовать K=10 и статус NOT_RUN_BUDGET_GATE для K=100. Вывод о полном пакете K=100 в такой области отсутствует. Прежние таймауты TSFG на миллионе не подменяют результат новой реализации.

### 10.3. Измеряемый выход и проверка

Основной выход SCHEDULE сохранить полным и одинаковым у обоих движков. Для расширений добавить времена входа в буфер, завершения обработки, освобождения станка и интервалы владения ресурсом. Включить формирование и запись выхода в T_batch и T_total. Размер вывода публиковать отдельно.

Отдельно записывать время загрузки, подготовки модели, самого расчёта и сериализации. Если позднее потребуется краткий выход только для миссии, определить новый профиль и повторить оба движка на одинаковом составе результата. Старые времена полного SCHEDULE с кратким выходом не смешивать.

Для каждого нового экземпляра проверить все сценарии независимым воспроизведением DES-EXT и внешними инвариантами. Сравнить индивидуальные поля с TSFG, затем сверить канонические хеши всех повторов. Хеширование результатов не заменяет проверку физических ограничений.

Хранить полные трассы Mk01 и всех расхождений. Для больших серий сохранять полные трассы M0 и трёх заранее выбранных сценариев каждого профиля; для остальных — проверенные хеши, индивидуальные сроки заказов, агрегаты, счётчики и статус проверки. Такой состав оставит возможность повторно оценить сроки миссии и опоздания без повторения движка. Для восстановления очередей во времени дополнительно нужны интервалы владения/ожидания либо журнал изменений; отсутствие этих данных отмечать явно.

### 10.4. Критерий скорости

Для каждой пары на одной VM использовать S=sqrt(T_DES,1×T_DES,2 / (T_TSFG,1×T_TSFG,2)). Основная величина использует T_total; T_batch привести отдельно. Объединять девять пар геометрическим средним G отдельно по семейству, размеру и профилю.

Подтверждение заявленного двукратного преимущества требует всех девяти завершённых корректных пар, G≥2 и геометрического среднего S>1 в каждом из трёх раундов VM. Показать все девять значений; не объединять разные размеры в один коэффициент. Любой отсутствующий результат исключает статус подтверждения в соответствующей области.

Таймауты сохранять как цензурированные времена. При завершённом эталоне можно вычислить границу отношения времён, но нельзя подставлять 300 секунд как фактическое полное время TSFG. Не объединять прежние абсолютные времена с новыми замерами в парные коэффициенты.

### 10.5. Память

Прежний ru_maxrss сохранить с уже опубликованным ограничением. Для новых завершённых процессов считывать VmHWM самого образа движка после exec, перед выходом. Проверить метод отдельным контрольным workflow на малой программе с известным распределением памяти. Для таймаутов снимать VmHWM после подтверждения запуска нужного образа; публиковать наблюдённый максимум и признак прерывания.

Пик всего job или контейнера вместе с генератором не приписывать движку. Новый способ измерения памяти не требует повтора всех прежних временных серий.

## 11. Четвёртый этап: проверить полезность резервов

Выполнить после повторного анализа E4 и допуска PBR. Основной показатель: доля завершённых заказов к D. Полное выполнение миссии и опоздание представить дополнительными показателями. Это уменьшит зависимость вывода от единственного бинарного исхода.

### 11.1. Разделить выбор конфигурации и оценку

Для каждого исследуемого экземпляра создать отдельные наборы сценариев: 100 калибровочных для срока, 100 для выбора вмешательства, 1000 оценочных. Использовать разные purpose генератора. Оценочную выборку открыть только после сохранения хеша выбранных конфигураций и критериев.

Для синтетического опыта нормировать интенсивности отказов и длительности ремонта относительно фиксированного C0, определённого до выбора D. Начальный закон: интервалы работоспособности экспоненциальны со средним 10C0; ремонт равномерен [0,01C0;0,03C0]. Общую причину задать отдельной серией: средний интервал 2C0, длительность 0,02C0, заранее выбранная группа. Зафиксировать независимость потоков и генерацию календарей до диагностического предела. После выбора D закон отказов не менять.

Сохранить D_fixed=1,10C0. Для дополнительного опыта с чувствительным сроком выбрать D_cal как медиану полных сроков базовой конфигурации на калибровочной выборке с округлением к ближайшему допустимому тику. Опубликовать обе серии. Если медиану нельзя установить из-за цензурирования или блокировок, чувствительную серию не объявлять подготовленной; сначала разобрать причину. При большом числе одинаковых сроков доля успеха может остаться крайней — это раскрыть без последующей подстройки по оценочной выборке.

На реальном производственном плане использовать установленный заказчиком срок. Синтетический D_cal служит проверке различимости вмешательств и не заменяет производственное обязательство.

### 11.2. Сравнить рекомендации с простыми правилами

Для изменения скорости одного станка на +10% сохранить точное преобразование времени ×11 и работы ускоренного станка ×10. Одинаковое процентное усиление считать равным техническим вмешательством; равенство денежных затрат без данных о стоимости не заявлять.

Сформировать список кандидатов: три первых ресурса по критичности отказа, три по номинальной загрузке и три по заранее заданному случайному выбору. Для изменённого PBR ранжирование рассчитать заново: старые ранги P0 не доказывают критичность в другой физической модели. Одинаковые кандидаты учитывать один раз.

На выборке выбора вмешательства оценить кандидатов и закрепить один вариант с наибольшим приростом выпуска. При равенстве использовать заранее установленный порядок идентификаторов. Такая рекомендация учитывает измеренный эффект усиления. Отдельно сохранить вариант, выбранный только по критичности отказа.

На 1000 новых сценариев сопоставить исходную конфигурацию, выбранное по эффекту усиление, первое по критичности, первое по загрузке и три случайных усиления. Совпадающие конфигурации запускать один раз и явно отмечать совпадение правил выбора.

Для каждой записи вычислить парные разности выпуска с исходной конфигурацией и с правилом максимальной загрузки. Представить вероятность улучшения и ухудшения, средний эффект, интервал и фактическое число выполненных миссий. Основной критерий полезности: нижняя граница парного 95%-го интервала выше нуля в обоих сравнениях и средний прирост к исходной конфигурации не меньше 0,01 от общего числа заказов. Порог 1% задаёт практическую значимость этого синтетического опыта.

При нескольких семействах принимать решения отдельно и раскрывать все сравнения; для общего статистического утверждения применить заранее закреплённую поправку Холма. Нулевая разность при совпадении выбранных станков означает отсутствие преимущества над данным простым правилом.

Начать с N=10 000. Подтверждающий размер N=100 000 запускать после проверки бюджета. Для нового полезностного опыта полный миллион операций не обязателен. Отдельно раскрывать, на каком размере установлены эффект рекомендаций и скорость вычисления.

### 11.3. Другие резервы и альтернативные маршруты

Следующими отдельными семействами вмешательств могут стать +1 место в конкретном буфере, +1 единица общего ресурса и заранее подготовленный альтернативный маршрут. Внутри одного сравнения использовать одинаковый тип и размер вмешательства. Пересчёт процентов скорости в стоимость буферного места требует внешних данных.

Альтернативный маршрут подготовить до отказов и проверить номинальную допустимость. Рассчитать базовый и альтернативный планы на одинаковых сценариях. Изменение C0 альтернативы не переносит срок D: сравнение использует общее производственное обязательство. Переназначение незавершённой операции во время отказа требует отдельной политики и в эту первую серию не входит.

### 11.4. Проверить объяснение каскада

Для заранее выбранных полных трасс построить цепочки ожидания по технологическому предшественнику, предыдущей операции станка, заполненному буферу и занятой единице общего ресурса. Сохранить все одновременно действовавшие ограничения; совпадение времён не устанавливает единственную причину задержки.

Сопоставить цепочку с M0 и сценариями снятия одного из нарушений. При наличии этих сценариев использовать готовые результаты. Для отсутствующего контрфактического варианта выполнить отдельный малый запуск в Actions. Проверить, что указанное изменение действительно сократило задержку или увеличило выпуск. Для взаимной блокировки сохранить проверяемую цепочку взаимного ожидания и учесть будущие восстановления. Эту проверку выполнить на ручном случае из этапа 6 и трёх заранее выбранных сценариях каждого нового профиля; массовая проверка всех возможных причин не входит в первый пакет.

## 12. Отдельная проверка потокового TSFG

Приложенный отчёт Ozon, раздел 6.2, допускает объединение ресурсов при полной совместимости работы с репликами, свободном выборе доступного ресурса и допустимом перераспределении работы. Ограничения совместимости и существенные затраты переключения требуют более подробной модели. Эти условия следует перенести в проверяемый контракт агрегации.

Прежняя G2 отбросила индивидуальную совместимость и фиксированный порядок операций. Её отрицательные результаты сохранить. Простое увеличение размера группы или шага времени не считается исправлением.

Проверку PF проводить отдельно от PBR:

1. Сохранить контроль Ozon healthy_100k и хеш исходного S1. Использовать опубликованные физические параметры только там, где они доступны и однозначны; недостающие параметры выписать до реализации.
2. Определить группу агрегации по маршруту, совместимости, длительности, поступлениям и правилу обслуживания. Любое отброшенное различие перечислить явно.
3. Для каждого случая выбрать статус: доказанная эквивалентность выбранных наблюдений либо приближение с измеряемой ошибкой. Целочисленные изделия, непрерываемая обработка и пороговые сроки требуют самостоятельной проверки даже при полной совместимости станков.
4. Начать с двух постановок: однородный последовательный поток и поток с объединением ветвей/конечным буфером. Для каждой задать благоприятный режим, ограничение мощности и близкий к предельному срок. Получатся шесть диагностических случаев.
5. Сопоставить S1 с независимым расчётом той же потоковой модели. Для кусочно-постоянных мощностей целесообразен событийный расчёт смены режимов, заполнения и опустошения буферов. При сравнении с поштучным DES дополнительно измерить ошибку перехода от дискретных изделий к потоку.

Допуск приближения установить до запуска: ошибка выпуска не больше 1% объёма, ошибка интеграла НЗП не больше 5%, ошибка известного Cmax не больше 1% C0, отсутствие ложных прогнозов выполнения на контрольной сетке. Очереди проверять на уровне действительно сохраняемых групп. При отсутствии индивидуальной очереди или срока пометить показатель UNSUPPORTED.

Для каждого конечного буфера требовать ошибку длины очереди не больше 5% вместимости; проверять снимок к D и максимум на горизонте. Для неограниченной очереди использовать порог max(1 единица материала, 5% эталонного максимума очереди). Все физические вместимости и баланс должны соблюдаться независимо от допуска приближения. Нормирование ошибки малой очереди на весь миллион операций недопустимо.

Для статистического утверждения о доле опасных пропусков использовать новые случайные сценарии и отдельно учитывать число фактических срывов n_fail. При нуле ложных успехов односторонняя 95%-я верхняя граница равна 1−0,05^(1/n_fail). Число всех запусков не подменяет знаменатель n_fail. На детерминированной сетке такая вероятностная интерпретация отсутствует.

После диагностического допуска возможны парные замеры PF. Ускорение относительно старого пооперационного TSFG само по себе не подтверждает преимущество над точным специализированным расчётом. Преимущество PF относится к утверждённым агрегированным показателям; индивидуальные сроки и маршруты требуют отдельного допуска.

PF не блокирует исправление промышленной серии PBR. Его первую фазу ограничить шестью диагностическими случаями; большую новую матрицу до установления области точности не запускать.

## 17. Дополнительная обязательная серия APS: построение плана

### 17.1. Новая цель

Измерить построение допустимого производственного расписания из 1 000 000 операций с выбором оборудования и очередности. Единица масштаба относится к операциям внутри одного плана. Показатель BFG APS на странице поставщика составляет 45 минут для такого заявленного количества операций; число сценариев к этому показателю не относится.

Эту серию выполнить независимо от доработки буферов PBR. Для первого APS-результата использовать имеющийся построитель schedule() из experiments/scale_data.py. Сейчас он работает внутри генератора: выбирает готовую операцию и альтернативный станок по минимальному допустимому началу, затем окончанию и фиксированным правилам разрешения равенств. Зафиксировать его как SHEAFT-LIST-v1, конструктивный алгоритм построения допустимого расписания. Название TSFG или DAG-REF этому алгоритму не присваивать.

DAG-REF использовать для независимой проверки уже построенного расписания и расчёта исполнения. Проверять отсутствие пересечений и допустимость назначений также отдельными инвариантами.

### 17.2. Повторное использование

Полные альтернативные станки и длительности сохранены в operations.jsonl.gz, указанном в inputs-index.json. Для APS-входа оставить идентификаторы операций и заказов, поступления, предшественников, альтернативы оборудования и длительности обработки. Удалить назначенный machine, выбранный work, planned_start, planned_end и готовые очереди. Запретить планировщику читать старый готовый план. Старое расписание сохранить отдельно как известное допустимое решение для контроля качества.

Получение входов и удаление полей выполнять отдельным подготовительным job в GitHub Actions. Хеш нового APS-входа закрепить до измерений. Время генерации синтетических маршрутов публиковать отдельно от времени построения расписания.

В manifest старой генерации предусмотрено generation_wall_s. Этот счётчик охватывает создание задания, построение плана, запись и сжатие файлов, подготовку сценариев. Проверить доступность сохранённых значений и раскрыть их как время старого подготовительного процесса. Они не дают отдельного времени schedule(). Основной APS-замер выполнить заново в выделенном процессе.

### 17.3. Матрица и измерения

Сначала проверить Mk01 и малые задания. Использовать сохранённый оптимум Mk01 C0=40 как оценку качества. Конструктивный алгоритм может получить более длинный допустимый план; такой результат сохранять, оптимальность не приписывать.

Основная матрица: F1/F2 × DENSE/SPARSE × N=100 000/1 000 000 × seed 101/102/103. Повторно использовать прежние реальные значения поступлений; не пересчитывать их по результату нового алгоритма.

Поскольку у F1/DENSE разные seed могут давать одинаковые задачи, группировать экземпляры по SHA-256 APS-входа. Идентичные входы считать техническими повторами одной задачи. Число seed само по себе не устанавливает число независимых задач.

Для каждого уникального входа выполнить три измерения на независимых GitHub-hosted VM с закреплёнными 1 CPU и 4 GiB. Основной предел процесса: 2700 секунд. Перед миллионом операций провести предварительный запуск на 100 тысячах и проверить потребление памяти. Сохранить ошибки и таймауты. Время сборки и генерации входов вынести за границы измерительного процесса.

Публиковать T_read, T_schedule, T_output и полное T_total от запуска процесса до готового файла расписания. Основное время для внешней сравнительной таблицы — T_total. Проверку независимым валидатором выполнять после измерения и публиковать отдельное время. Невалидный план не получает допуска независимо от скорости.

Не заменять построение плана чтением готовых очередей или воспроизведением номинального исполнения. Прежние 21,5–39,8 секунды в APS-таблицу не переносить.

### 17.4. Качество расписания

Для каждого результата сохранить Cmax, отсутствие нарушений, загрузку станков, машинные очереди и нижнюю оценку Cmax. На малых экземплярах сопоставить результат с CP-SAT и сохранёнными доказанными оптимумами. Опубликованная документация OR-Tools определяет ограничения предшествования, непересечения операций на машине и минимизацию полного срока для базовой job-shop-постановки: https://developers.google.com/optimization/scheduling/job_shop.

На больших экземплярах использовать доказуемые нижние оценки: длительность критического технологического пути с минимальными допустимыми работами, суммарную минимальную работу на число станков и обязательную нагрузку замкнутых групп оборудования на число станков группы. Проверить применимость каждой оценки к конкретному входу. Нагрузку выбранного алгоритмом отдельного станка нельзя без обоснования считать нижней оценкой задачи с альтернативными назначениями.

В таблице привести gap=(Cmax−LB)/LB и отношение к Cmax прежнего допустимого плана. Значение gap=0 при корректной нижней оценке и допустимом плане доказывает оптимальность Cmax данной модели. Положительный gap не доказывает, что решение хуже оптимума именно на эту величину; это верхняя оценка относительного разрыва до оптимума.

Первый профиль APS-BASIC включает поступления, технологические зависимости, альтернативное оборудование и ограничение одной операции на станке. Для переналадок, календарей обслуживания, начального НЗП, комплектующих и общих ресурсов поставить отдельные отметки реализации и проверки. Полный набор возможностей BFG нельзя приписывать APS-BASIC по одному совпадению числа операций.

### 17.5. Сопоставление с BFG

В итоговой презентационной таблице разделить происхождение данных: BFG APS — опубликованное поставщиком значение 45 минут; Sheaft SHEAFT-LIST-v1 — измеренное T_total с указанием входа, ограничений, качества расписания и оборудования. На странице BFG не раскрыты достаточные сведения о конкретном тестовом входе, вычислителе и качестве решения для воспроизведения этого замера.

Если условия не удалось выровнять, таблица содержит два результата разных испытаний. Деление 2700 секунд на T_total Sheaft даёт отношение опубликованных времён; доказанным ускорением на общей задаче оно не становится. Подтверждение прямого преимущества над BFG потребует сопоставимого входа, качества и оборудования либо воспроизводимого протокола поставщика.

Принадлежность BFG классу APS или использование определённого типа алгоритмов не устанавливают верхнюю границу производительности остальных участников класса. Даже подтверждённое превосходство над BFG не доказывает превосходства над всеми APS. Для общего утверждения потребовалось бы определить класс и доказать результат для всех его участников; измерение одного представителя этого не делает.

### 17.6. Исполнение

Добавить workflow aps_schedule_benchmark.yml с этапами prepare, correctness, measure, validate, report. Независимое получение артефактов и сравнение с прежними допустимыми планами выполнить в Actions. Приватный S1 для измерения SHEAFT-LIST-v1 не требуется.

Выход серии: aps-inputs-index.json, aps-processes.csv, aps-quality.csv, отдельный отчёт с происхождением показателя BFG и таблицей поддержанных ограничений. Ни один APS-запуск при подготовке этой редакции плана не выполнен; значение N для презентации пока неизвестно.
