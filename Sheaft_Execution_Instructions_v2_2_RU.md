Получить два самостоятельных результата:

1. **APS:** время построения нового допустимого плана из миллиона операций, характеристику качества плана и сопоставление с опубликованными 45 минутами BFG APS. Принять BFG первым рыночным ориентиром; распространение предполагаемого преимущества на класс APS сохранить как рыночную гипотезу.

## 4. PR 3: зафиксировать точную семантику PBR

### 4.1. Сетка времени

Новая версия семантики: `PBR-EXACT-v2.2`. Для Mk01 один входной тик равен 0,01 исходной единицы Mk01; для F1/F2 один тик равен 0,01 секунды синтетической модели. Не переводить единицы Mk01 в секунды без отдельного основания.

Фактический шаг S1 в новой точной серии: **Δ=5 входных тиков**. Операции с единичной скоростью, поступления, нижние границы начала, воздействия и горизонт обязаны быть кратны 5. Уже сохранённые v1-входы сохранить без изменений; несовместимая сетка получает отдельный профиль и регрессию.

Для неотрицательного рационального x определить `R5(x)=5×floor(x/5+1/2)`. Половину округлять вверх; вычислять через целые числитель/знаменатель. Начало воздействия: `R5(a×C0)`; длительность: `max(5,R5(b×C0))`; конец: начало плюс длительность. Сдвинутый отказ ресурса начинается в `R5(начало+длительность/2)`. `R(m)=mean_s[(Q0(D_fixed)−Q_m,s(D_fixed))/J]`.

Сортировать по убыванию R, равенства разрешать минимальным machine_id. Сохранить отрицательные значения: при фиксированных очередях исключать их заранее нельзя. Выпуск к сроку остаётся определённым при доказанном DEADLOCK; вычислительный таймаут записи не даёт. Отказная критичность и польза ускорения имеют отдельные поля.

Контроль загрузки: `U_processing(m)=время фактической обработки в M0/C0`. Удержание готовой детали публиковать отдельно как `U_blocked(m)`. Основной выбор по загрузке использует только U_processing.

Кандидаты: первые три по R, первые три по U_processing и первые три из перестановки станков по SHA-256 строки `v2.2|random-control|task_sha256|machine_id`. Выбирать случайные контроли из всех станков до просмотра эффектов. Объединить совпадающие id. На 100 сценариях выбора сравнить прирост выпуска при ускорении одного станка на 10%; выбрать максимальное среднее Δq к D_fixed, равенства разрешить по machine_id.

На 1000 оценочных сценариях проверить базу, выбранное усиление, первое по R, первое по U_processing и три случайных. Совпадающие конфигурации считать один раз, связь с правилами выбора сохранить. Число уникальных конфигураций не больше семи.

### 7.3. Статистика до открытия оценочного банка

Первичные парные величины: `d_base=(Q_selected−Q_base)/J`, `d_load=(Q_selected−Q_load)/J`. Единица наблюдения — целый сценарий со всеми конфигурациями. Для каждой области нужны все 1000 полных записей выпуска; timeout/OOM/error дают `INCOMPLETE`, соответствующие проверки получают p=1 в общей семье. Выпуск при остановке точно на D — полное наблюдение этого показателя.

Для каждого среднего эффекта построить percentile-bootstrap интервал 95%: 10 000 выборок размера 1000 с возвращением, квантиль методом linear, paired resampling. Использовать общий массив выбранных индексов для обоих сравнений и сроков внутри области. Сохранить seed и версии библиотек.

Для общей проверки использовать односторонний парный t-test гипотезы E[d]≤0: `t=mean(d)/(sd(d)/sqrt(n))`, p по t-распределению с n−1 степенями свободы. Это заранее выбранная приближённая проверка среднего на независимых сценариях. Если sd=0 и mean≤0, p=1; если sd=0 и mean>0, использовать консервативную ограниченную оценку `p=exp(−n×mean(d)^2/2)` для d∈[−1,1]. Вырожденность интервала раскрыть.

Семья Холма фиксируется как **32 проверки**: 2 семейства входов × 2 размера × 2 срока × 2 закона × 2 сравнения. Для недопущенного размера или неизвестного D_cal оставить p=1; размер семьи после просмотра результатов не уменьшать. Проверить p_(i)≤0,05/(32−i+1) последовательно до первого отказа. Опубликовать исходные и скорректированные p.

Критерий полезности в конкретной области: средний d_base≥0,01, обе нижние границы парных 95%-х интервалов выше нуля и обе проверки прошли Холма. Дополнительно сохранить медианы, доли улучшений/ухудшений и число полностью выполненных заданий. Совпадение выбранного станка с контролем загрузки даёт нулевой d_load и отсутствие установленного преимущества над этим правилом.

Перед каждой размерной ступенью оценить стоимость по пяти калибровочным сценариям. Для допуска умножить максимальное время сценария на фактическое число запусков всех конфигураций, добавить ранжирование 200×15 проб на вход и коэффициент запаса 2. Расходы валидации и диагностики включить. Оставшийся бюджет должен покрыть всю обязательную оценку области.

## 8. PR 8: PF и итоговые статусы

PF ограничить шестью диагностическими случаями плана 2.1: два типа потоковой постановки × благоприятный, ограниченный по мощности и близкий к предельному сроку режимы. До моделирования зафиксировать совместимость, перераспределение работы и наблюдаемые величины. Проверять независимым расчётчиком той же физической постановки.

Пороги сохранить: выпуск ≤1% объёма; интеграл НЗП ≤5%; известный Cmax ≤1% C0; очередь конечного буфера ≤5% вместимости; очередь без ограничения ≤max(1 единица,5% эталонного максимума). Проверить снимок к D и максимум очереди. Баланс и вместимость обязательны при любом допуске. На контрольной сетке требовать отсутствие ложных успехов.

Для новых случайных сценариев знаменатель опасных пропусков равен числу фактических срывов `n_fail`. При нуле ложных успехов и n_fail>0 верхняя односторонняя 95%-я граница равна `1−0,05^(1/n_fail)`. При n_fail=0 присвоить `NOT_ESTIMABLE`. Большую PF-матрицу до установления области точности не запускать.

Финальный сборщик раздельно проверит наличие обязательной APS, PBR-корректности, предварительных измерений, больших допущенных серий, резервов и диагностики PF. Наличие раздела в плане не подтверждает выполнение серии.

Использовать независимые поля статуса:

- `execution_status`: COMPLETE / PARTIAL / NOT_RUN;
- `correctness_status`: VALID / INVALID / UNCHECKED;
- `performance_status`: MEASURED / TIMEOUT / OOM / NOT_RUN_BUDGET_GATE;
- `hypothesis_status`: SUPPORTED / NOT_SUPPORTED / INCONCLUSIVE / NOT_APPLICABLE;
- `quality_status` для APS: OPTIMAL_CERTIFIED / GAP_BOUNDED / QUALITY_UNKNOWN.

Workflow может успешно собрать отчёт с отрицательным результатом. Неполная обязательная серия сохраняет PARTIAL; технический success это поле не изменяет.

## 9. Бюджет и управление запусками

Предельный бюджет кампании по этой инструкции: **48 runner-часов GitHub Actions**, включая подготовку, сборки, проверки, повторы и публикацию. Это установленный предел будущей кампании. Тариф и денежная стоимость здесь не оценены. При параллельных job суммировать их время; календарная длительность workflow не заменяет расход runner-времени.

| Часть кампании | Предел runner-часов |
|---|---:|
| Первый пакет PR 1–4: E4 ≤1; APS ≤4; корректность PBR ≤2; предварительная PBR ≤3 | 10 |
| PR 5: оставшаяся APS-матрица | 12 |
| PR 6: PBR на 100 тысячах и миллионе, включая проверки | 16 |
| PR 7: ранжирование, выбор и оценка резервов | 8 |
| PR 8: PF и итоговый отчёт | 2 |
| **Всего** | **48** |

Для сравнения с прежней редакцией: 24 APS-входа × 3 повтора × 2700 секунд давали предел 54 часа только измерительных процессов. После дедупликации он равнялся 2,25U часа. В этой инструкции предел 100-тысячного APS-процесса снижен до 180 секунд; предел миллионного остался 2700. Фактическая верхняя граница полной матрицы процессов равна `0,15U_100k+2,25U_1m` часа до зачёта уже выполненных повторов. Она может превысить бюджет; поэтому допуск оценивает оставшуюся стоимость и сохраняет пропуски.

Для предварительной PBR M0 и K=10 выполняются отдельными процессами: 36×2 движка×2 процесса×60 секунд = 2,4 часа времени процессов. Два основных размера PBR дают максимум 12 часов измерительных процессов. Оставшиеся часы соответствующих пакетов покрывают подготовку и проверку; превышение этого резерва блокирует дальнейший запуск.

Создать `budget-v2.json` с лимитами и `budget-ledger.jsonl` с фактическим и зарезервированным временем job. Перед отправкой очередной группы резервировать полный timeout всех job; после завершения освобождать неизрасходованный остаток. Сначала выполнять прогнозируемые короткие группы, заранее фиксируя их порядок в manifest. Массовую матрицу, сумма timeout которой превышает остаток, одновременно не отправлять.

При нехватке лимита сохранить `NOT_RUN_BUDGET_GATE` и продолжить независимые части в пределах их лимитов. Автоматический повтор экспериментального timeout/OOM запрещён. Для сбоя инфраструктуры допустим один повтор с отдельным id, если он помещается в остаток. Лимиты между пакетами автоматически не переносить.
