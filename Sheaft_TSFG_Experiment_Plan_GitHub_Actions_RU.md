# Sheaft / TSFG: протокол экспериментов по устойчивости производственного расписания

**Версия:** 1.1. **Дата:** 26 сентября 2026 года.  
**Статус:** предварительно заданные правила эксперимента; выполненные кампании и их допуск фиксируются отдельно в README и отчётах Actions.  
**Среда исполнения:** исключительно GitHub Actions на GitHub-hosted runners. Сборка, генерация данных, тестирование, моделирование, замеры и подготовка отчётов выполняются в workflow. Локальные запуски реализации и экспериментов исключены.

Числа сценариев, пороги погрешности и требования к ускорению ниже заданы для предстоящего исследования. Они не описывают уже достигнутые характеристики Sheaft.

**Дополнение 1.2 о реализации:** основной TSFG использует существующее Go-ядро S1
с новым адаптером фиксированных операций. [Нормативное описание переиспользования](docs/TSFG_REUSE_RU.md)
заменяет исходный выбор самостоятельного C++ GRID как основного участника.
Контракт операций и критерии приёмки сохранены. Самостоятельный GRID остаётся
вспомогательным контролем. Все выводы должны явно называть фактически исполненный участник.

**Первый законченный результат:** спецификация TSFG-OP-GRID, прохождение E0-core и Mk01 — 481 диагностическая траектория при Δ=0,05 и 1 443 проверки исхода для трёх сроков на движок. E1X, E2–E4 и непосредственные сравнения продуктов остаются следующими этапами. Их трудоёмкость и вычислительный бюджет пересчитываются после первого отчёта Mk01.

**Изменения версии 1.1:** добавлена [нормативная спецификация TSFG-OP-GRID](TSFG_OP_SPEC_RU.md); уточнены генератор и отдельный профиль BURST; DAG включён в основную процедуру замеров; классы точности разделены по горизонту и выходу; H3 рассчитывается по самостоятельным завершённым запускам K=100; E0 разделён на core/extended; заранее определены ранжирование ресурсов и критерий H5. Пороги и результаты версии 1.0 не переносятся автоматически на новую кампанию.

## 1. Назначение исследования

Проверить применимость Temporal Stochastic Flow Graph, TSFG, к анализу исполнения заранее выбранного производственного расписания. Расписание определяет операции, назначенные станки и очередность обработки. Нарушения изменяют фактические сроки исполнения. Основная серия сохраняет принятые назначения и очередность.

Исследование должно ответить на следующие вопросы:

1. Воспроизводит ли TSFG сроки отдельных операций и заказов при отказах оборудования и увеличении длительности обработки?
2. Какие одиночные и совместные нарушения приводят к невыполнению задания к установленному сроку?
3. Где возникают очереди и какие операции передают задержку другим заказам через общий станок?
4. Как изменятся результат и вычислительные затраты при росте задания до миллиона индивидуальных операций?
5. Какую погрешность внесёт агрегация и оправдает ли ускорение потерю детализации?
6. Какие изменения мощности, резервирования или буферов уменьшат число срывов при неизменном сроке задания?

Прикладной результат пилота: перечень уязвимых ресурсов, сценарии срыва, объяснение задержек и сравнение допустимых изменений производства. Вычислительный результат: воспроизводимые зависимости времени и памяти от размера задания, числа сценариев и детализации модели.

### Мотивация выбранной последовательности

| Этап | Проверяемое свойство | Причина включения |
|---|---|---|
| Малые контрольные примеры | Правила времени, занятия станка и завершения операции | Ошибку в этих правилах легко скрыть правильным итоговым выпуском |
| Mk01 | Индивидуальные операции и каскады при общих станках | Открытая небольшая задача с проверяемым расписанием |
| Расширение Mk01 | Буферы, деградация мощности, дефицит ресурсов | Эти ограничения отсутствуют в исходном экземпляре |
| Синтетические задания до 1 млн операций | Масштабируемость на общей производственной системе | Изолированное размножение маленьких задач недостаточно для проверки конкуренции за ресурсы |
| Агрегация | Соотношение скорости и погрешности | Именно сокращение состояния может дать TSFG вычислительное преимущество |

Mk01 остаётся обязательным первым производственным испытанием. Кейс «Робозон» служит дополнительным испытанием агрегированных потоков; переход к нему не заменяет проверку индивидуальных операций.

## 2. Исходные факты и границы выводов

### 2.1. Что установлено по TSFG

В приложенном отчёте «Временной стохастический потоковый граф сортировочного центра» описаны состояние оборудования, очереди, задержанные потоки, ремонт и критерий выполнения миссии на конечном горизонте [S1].

В §3.4 отчёта обслуживание агрегированной очереди задано объёмами типов материала. Порядок отдельных товаров внутри очереди не сохраняется. В §6.2 объединение ресурсов допустимо при совместимости каждой единицы работы со всеми ресурсами группы, отсутствии задержки выбора и возможности передачи работы между ресурсами. При других условиях отчёт предусматривает отдельные узлы.

Для производственного расписания потребуется явно хранить идентичность операции, оставшуюся работу и порядок занятия станков. Успех агрегированной модели сортировочного центра сам по себе не подтверждает корректность такого расширения.

Отчёт S1 предоставлен и прочитан; его наличие не заменяет спецификацию пооперационного исполнения. TSFG-OP-GRID версии 1.1 определён в отдельном нормативном документе как новое исследовательское расширение. Его порядок атомарных завершений и запусков не тождественен обслуживанию агрегированных объёмов из §3.4 S1. Само добавление индивидуальных операций не доказывает ускорения.

В §7 отчёт связал численный коэффициент ускорения с измерениями обеих реализаций на одинаковых данных и оборудовании. Готового сопоставимого замера TSFG и производственного DES в предоставленном отчёте нет.

### 2.2. Что установлено по конкурентам

| Источник | Опубликованное утверждение | Как использовать в исследовании |
|---|---|---|
| BFG APS [S2] | Построение производственного плана на 1 млн операций за 45 минут | Ориентир для выбора масштаба. Для отношения скоростей потребуются воспроизводимые условия построения плана |
| BFG Group [S3] | Собственная платформа с дискретно-событийным и агентным моделированием | Основание включить DES в сравнение методов |
| PlantTwin [S4, S5] | Моделирование исполнения внешнего расписания, сценарный анализ и Монте-Карло | Прямое функциональное пересечение с предлагаемым пилотом |

45 минут BFG относятся к построению расписания. Время проверки готового расписания нельзя делить на эту величину и объявлять полученное отношение ускорением относительно BFG.

В просмотренных материалах не найден единый публичный набор данных, на котором BFG и PlantTwin опубликовали скорость одной и той же задачи проверки отказов. Общий класс движка также не задаёт верхнюю или нижнюю границу быстродействия продукта.

## 3. Гипотезы и критерии решения

| Код | Гипотеза | Проверка | Условие принятия |
|---|---|---|---|
| H1 | Пооперационный TSFG сохраняет семантику фиксированного расписания | E0-core и 481 сценарий Mk01 | Выполнены все инварианты; в завершённых диагностических траекториях совпали начала и окончания всех операций |
| H2 | Точный пооперационный TSFG верно определяет выполнение задания к сроку | 1 443 проверки Mk01 и сопоставление исходов используемых сценариев | Ноль ложных успехов и ноль ложных срывов |
| H3 | TSFG сокращает время серии проверок | Самостоятельные K=100, отдельно относительно DES-REF и DAG-REF | Вычислимые критерии §12.5 выполнены на всех обязательных завершённых корректных точках, отдельно для каждого размера |
| H4 | Агрегация даёт дополнительное ускорение при контролируемой ошибке | Сравнение пооперационной и агрегированной версий | Выполнен заранее выбранный класс точности; показана зависимость ошибки от степени агрегации |
| H5 | Диагностика уязвимых ресурсов пригодна для выбора изменения | Фиксированное ранжирование; вмешательства на критичных и контрольных ресурсах при равных затратах | На независимой оценочной серии выполнены условия эффекта и преимущества над контролем из §13.2 |

H1 и H2 обязательны до публикации утверждения об ускорении корректного пооперационного расчёта. H3 может не подтвердиться. H4 может подтвердиться только для части семейств данных. Отрицательные результаты входят в итоговый отчёт.

Пороги ускорения относятся к исследовательской цели. Они не задают обязательную характеристику будущего коммерческого продукта.

## 4. Единая постановка задачи

### 4.1. Сущности

Для операции i задать:

- идентификатор операции и заказа;
- технологических предшественников;
- список допустимых станков и длительность на каждом из них;
- назначенный станок m(i);
- плановое начало s0(i);
- позицию в фиксированной очереди назначенного станка;
- объём оставшейся работы;
- фактические моменты начала, завершения обработки и освобождения станка.

Заказ содержит выпускной критерий и срок. Станок имеет календарь доступности, текущий коэффициент производительности и ёмкость одновременной обработки, равную одной операции в основной серии.

**Одна операция** в счётчике N означает отдельный экземпляр обработки с собственным идентификатором и состоянием. Число типов операций, число деталей и число событий календаря хранить отдельными полями. Миллион экземпляров операций должен присутствовать во входном наборе независимо от последующей агрегации.

### 4.2. Исполнение неизменного плана

Операция начинает работу при одновременном выполнении условий:

1. Наступило плановое начало и время доступности исходного материала.
2. Завершены все технологические предшественники.
3. Завершена предыдущая операция фиксированной очереди станка.
4. Станок доступен и свободен.
5. Доступны дополнительные ресурсы, если они включены в соответствующую серию.

Начинать операции раньше s0(i) запрещено. Готовые поздние операции не обходят задержавшуюся раннюю операцию в очереди. Этот выбор закрепляет объект исследования: устойчивость конкретной очередности.

Отказ останавливает текущую обработку. Станок сохраняет оставшуюся работу; после ремонта обработка продолжается. Брак, повторное выполнение с начала и миграция незавершённой операции в основную серию не входят.

Переназначение станков разрешить только в отдельной серии восстановления с явно заданным правилом.

### 4.3. Время и одновременные события

Интервалы занятости и отказа трактовать как полуоткрытые: [начало, окончание). Операция, завершившая обработку точно в момент начала отказа, считается завершённой.

На одной временной отметке:

1. Учесть работу, выполненную до этой отметки, и завершения операций.
2. Применить поступления материалов и освобождения ресурсов.
3. Одновременно обновить состояния отказов, ремонта и производительности.
4. Выполнить допустимые мгновенные передачи.
5. Запустить готовые операции в детерминированном порядке по идентификаторам ресурсов и операций.

Мгновенные передачи повторять до устойчивого состояния. Все длительности обработки положительны. Объединять перекрывающиеся интервалы недоступности одного станка; повторно вычитать мощность запрещено.

Последний шаг TSFG обрезать точно по D либо по пределу диагностического горизонта. Округлять срок миссии вверх до следующего полного шага запрещено.

Файл сценария содержит уже сгенерированные воздействия. Все сравниваемые реализации читают одинаковые события. Независимое потребление случайных чисел внутри движков исключено.

### 4.4. Критерий выполнения задания

Пусть C0 — завершение исходного допустимого плана, D — срок задания. Основной вариант: D = 1,10 × C0. Дополнительно оценить D = C0 и D = 1,25 × C0.

Миссия выполнена, если к D закончены все обязательные конечные операции, соблюдены ресурсные ограничения и сохранён материальный учёт.

Для основной серии единого задания все заказы имеют общий D. Индивидуальные сроки добавить в отдельное семейство данных и раскрыть правило их назначения.

Два режима расчёта:

| Режим | Остановка | Результат |
|---|---|---|
| MISSION | К сроку D; допускается ранний выход, если всё задание уже завершено | Выпуск к сроку, незавершённые заказы, очереди, исход миссии |
| DIAGNOSTIC | До завершения либо до 10D | Полные сроки и цепочки задержек; при достижении предела срок считается неизвестным и превышающим предел |

Основные замеры скорости выполнять в MISSION. Mk01 проверять также в DIAGNOSTIC. В таблицах производительности режимы не смешивать. Взаимную блокировку выделять отдельным исходом; достижение временного предела само по себе блокировку не доказывает.

### 4.5. Инварианты

- Каждая обязательная операция имеет ровно один корректный статус.
- Один станок не обрабатывает две операции одновременно.
- Предшественники завершены до начала зависимой обработки.
- Объём оставшейся работы неотрицателен.
- Завершённые операции не выполняются повторно.
- Обработка в интервале полной недоступности отсутствует.
- Целые изделия не превращаются в дробные завершённые экземпляры.
- Для сборки соблюдены количество и идентичность входных компонентов.
- При конечных буферах их заполнение не превышает вместимость.

Проверки инвариантов включены в валидационные запуски. Для измерений времени допускается отключить дорогую подробную диагностику одинаково у всех сравниваемых движков; обязательные выходные показатели сохраняются.

## 5. Реализации и независимость эталонов

### 5.1. Состав стенда

| Компонент | Назначение |
|---|---|
| TSFG-OP | Основной алгоритм tsfg-op-grid-v1.1 по отдельной нормативной спецификации |
| TSFG-AGG | Агрегированные представления с явно описанными допустимыми объединениями |
| DES-REF | Независимая событийная реализация той же производственной семантики |
| DAG-REF | Расчёт сроков по ациклическому графу технологической и станочной очередности |
| SimPy-REF | Небольшой независимый эталон для Mk01 и контрольных примеров |
| Генератор | Исходные задания, допустимые расписания и файлы воздействий |
| Проверяющий модуль | Инварианты, расхождения, итоговые таблицы |

Для исследовательских ядер TSFG-OP, TSFG-AGG, DES-REF и измеряемого DAG-REF использовать C++20 с одинаковым компилятором и параметрами оптимизации. Python использовать для подготовки данных, OR-Tools, малой модели SimPy и отчётов. Всё исполняется в Actions.

Если доступная реализация TSFG использует другой язык, включить её отдельным участником. Перенос TSFG на C++ должен пройти сопоставление с исходной реализацией на общих примерах. До получения исходного кода реконструкцию по отчёту обозначать как новую исследовательскую реализацию описанной модели. Её результаты нельзя автоматически приписывать существующей версии продукта.

### 5.2. Условия для сильного DES-эталона

- Обрабатывать завершения, поступления и изменения доступности через календарь событий.
- Исключить проход по всем операциям при каждом событии.
- Хранить индексы непосредственно затронутых операций и ресурсов.
- Не помещать в календарь события для каждого кванта неизменного состояния.
- Использовать компактные массивы и идентификаторы вместо неоправданно тяжёлых объектов.
- Собирать оптимизированную версию; запретить сравнение с отладочной сборкой.
- До основных замеров проверить два варианта организации календаря: общую очередь и очередь с объединением событий одной временной отметки. Выбор зафиксировать по отдельным калибровочным данным.

Код движков не должен вызывать друг друга. Допустим общий модуль чтения файлов, преобразования единиц и вычисления итоговых метрик. Логику продвижения времени и обработки операций реализовать независимо.

DAG-REF применим в основной постановке с фиксированными очередями, неограниченными буферами и без дополнительных конкурирующих ресурсов. Для сценариев изменения длительностей он даёт прямой расчёт по предшественникам. При отказах можно дополнить его независимой функцией завершения работы на заданном календаре станка. Конечные буферы и динамическое переназначение требуют отдельного эталона DES.

Превосходство только над SimPy недостаточно для общего вывода о быстродействии метода: особенности реализации и языка попадут в тот же коэффициент ускорения. Документация SimPy описала последовательную обработку событий и календарь на двоичной куче [S9].

### 5.3. Нормативный алгоритм TSFG-OP

До реализации ядра применяется [TSFG_OP_SPEC_RU.md, версия 1.1](TSFG_OP_SPEC_RU.md). Документ определяет неизменные входы, состояние, целочисленное время, атомарные завершения, обработку границ отказов, старты, остановку и состав обхода.

На станке хранятся текущая операция, остаток работы и указатель фиксированной очереди. На шаге обходятся станки; при завершении обновляются только непосредственные технологические последователи. Начальная подготовка и сброс сценария могут обходить N операций. Полный обход N внутри каждого шага основного алгоритма запрещён.

Без подробной диагностики верхняя оценка прохода и сброса одного сценария — O(N+E+L+M·ceil(H/Δ)), где M — станки, E — технологические связи, L — подготовленные воздействия. Это характеристика выбранного алгоритма, не доказательство ускорения. В F1 при миллионе операций C0≥280 000 секунд; полный обход N на каждом шаге 1 секунда потребовал бы не менее 2,8×10^11 посещений операций в исходном сценарии. Такой способ реализации не является основным GRID.

Пропуск пустых интервалов, внутренний календарь и приблизительное округление получают отдельные algorithm_id, спецификации и валидацию. До их появления ни один такой вариант не включается под именем GRID. Первый результат охватывает только точный GRID при Δ=0,05 на Mk01.

Минимальный комплект каждого экземпляра:

Для Mk01 достаточно текстовых таблиц и JSON. Для миллиона операций предусмотреть версионированный бинарный формат с описанной схемой и небольшим текстовым образцом. Все движки читают один и тот же набор.

Время исходного Mk01 измерять в условных единицах. Производственные часы или минуты ему не приписывать. Синтетическим большим заданиям назначить секунды; это соглашение генератора.

Для Mk01 хранить время в целых сотых исходной единицы. Для E2 хранить целые сотые секунды, хотя операции и воздействия основной серии кратны секунде: сроки 1,10C0 и 1,25C0 могут быть дробными. D и 10D вычислять точно целочисленными отношениями; шаг 1 секунда равен 100 тикам. При дробных скоростях в расширении отдельно определять численное представление завершения работы.

### 6.2. Случайность

Корневой seed кампании: 20260926. Идентификаторы наборов: 101, 102, 103. Для калибровки использовать 901 и 902; в итоговые сводки их не включать.

Производные seed получать из SHA-256 канонической строки с полями root_seed, protocol_version, dataset_id, scenario_id, purpose. Закрепить кодировку UTF-8 и разделитель «|»; идентификаторы не должны содержать разделитель. Первые 16 байт хеша трактовать как беззнаковое число little-endian для NumPy PCG64. Использовать отдельно именованные потоки для маршрутов, длительностей, отказов и восстановления.

Версию генератора и библиотек сохранить. Главный источник воспроизведения — опубликованные входные файлы и контрольные суммы; одного числа seed недостаточно.

### 6.3. Выходной контракт

Для каждого сценария сохранить поля выбранного output_profile и служебные сведения о запуске. Полный набор FULL перечислен ниже; очереди, интегралы и разложение ожиданий не обязательны для SCHEDULE и не должны скрыто расширять его выход:

- исход миссии, выпуск к D и число незавершённых заказов;
- сроки заказов либо отметку об отсутствии завершения до предела;
- максимальные очереди и интеграл незавершённого производства по времени;
- суммарное ожидание, обработку, простой и блокировку станков;
- проверку инвариантов, число расхождений с эталоном;
- время подготовки модели, первого сценария и серии;
- CPU time, максимальный RSS, счётчики событий или временных шагов;
- статус OK, INCORRECT, TIMEOUT, MEMORY_LIMIT, DEADLOCK либо INFRA_FAILURE;
- идентификаторы коммита, workflow, попытки запуска и входных файлов.

Каждый результат также содержит algorithm_id, output_profile, accuracy_profile, горизонт метрик и сведения о цензурировании сроков. Основной контракт SCHEDULE включает индивидуальные времена, статусы и остатки работы к горизонту, сроки заказов, выпуск и исход миссии. FULL добавляет очереди и интегралы; AGG-MISSION содержит заранее заданные агрегированные показатели без обещания индивидуальных времён. UNSUPPORTED относится к полю, CENSORED — к неизвестному сроку, а не к статусу завершения процесса.

В MISSION неизвестное окончание хранить как null с отдельной строгой нижней границей D. В DIAGNOSTIC при пределе — null с границей 10D. Не подставлять предел вместо фактического срока. Для очередей и интегралов MISSION общий интервал — [0,D], включая корректное дополнение после раннего завершения. В самостоятельном MISSION и проекции DIAGNOSTIC одинаково обработать всю отметку D, в том числе старты точно в D без последующей обработки за горизонтом.

Подробные пооперационные результаты хранить для Mk01 полностью. На миллионе операций выполнять проверку массивов по одному сценарию, записывать сводки и хеши; полную трассу сохранять для первого расхождения и заранее заданной контрольной выборки. Хеш сам по себе не устанавливает величину численной ошибки.

Очередь станка считать по физически готовым и ожидающим обработки операциям. Будущие операции фиксированной очередности, для которых ещё отсутствует деталь, в этот показатель не входят. Дополнительно хранить число готовых операций, задержанных правилом очередности.

В основной цепочной постановке незавершённое производство считать как число поступивших, но ещё не завершённых заказов; интеграл измерять в заказо-секундах или заказо-единицах времени Mk01. Для сборочного семейства отдельно учитывать физические компоненты по типам. Показатели разных размерностей не складывать. Производственную загрузку станка считать по времени обработки; блокировку, ремонт и ожидание раскрыть отдельно.

## 7. E0-core и E0-extended: контрольные примеры

До Mk01 реализовать E0-core — небольшой набор вручную проверяемых случаев основной семантики:

| Пример | Проверяемое правило |
|---|---|
| Один станок, операции длительностью 3 и 2 | Исходное завершение в момент 5 |
| Тот же станок, отказ [1, 3) | Продолжение оставшейся работы; завершение задания в момент 7 |
| Отказ начинается точно в момент завершения первой операции | Завершённая операция сохранена; следующая ждёт восстановления |
| Два заказа претендуют на один станок | Исключительное занятие ресурса и фиксированная очередность |
| Два станка работают параллельно | Отсутствие искусственной общей блокировки |
| Задержанный предшественник ранней операции | Запрет обхода этой операции поздней готовой работой |
| Две ветви сходятся в сборочную операцию | Ожидание обоих компонентов |
| Два перекрывающихся отказа одного станка | Корректное объединение недоступности |
| Завершение точно в D и на один тик после D | Успех в первом случае, срыв во втором; неизвестный срок в MISSION не заменяется D |
| Старт точно в D | Начало сохранено, обработка после D отсутствует; совпадает проекция DIAGNOSTIC |
| Одновременные завершения двух предшественников сборки | Все завершения фиксируются до запусков; отсутствие лишнего шага ожидания |
| Раннее завершение всей миссии | Метрики MISSION имеют общий горизонт [0,D] |
| Увеличение работы или расширение интервала отказа | В основной фиксированной постановке окончания не становятся раньше |

Перед соответствующими расширениями выполнять E0-extended: заполненный межоперационный буфер, конкурирующие передачи, удержание и освобождение станка; недоступность дополнительного ресурса до старта и во время обработки; дробная скорость и согласованность её численного представления. E0-extended не блокирует основной Mk01, но обязателен для допуска своей серии E1X.

Численные ответы первых примеров выведены из заданных правил; они не представляют результаты выполненного программного теста.

E0-core должен пройти в Actions на TSFG-OP, DES-REF, DAG-REF и SimPy-REF. E0-extended проходит на реализациях, поддерживающих конкретное расширение; ограничения DAG раскрываются. Расхождение блокирует допуск соответствующей серии и её измерения скорости.

**Мотивация:** совпадение общего выпуска на крупной задаче может скрыть неверную обработку границ отказа, двойное использование станка или потерю индивидуальных деталей.

## 8. E1: базовый эксперимент на Mk01

### 8.1. Подготовка расписания

Использовать экземпляр Brandimarte Mk01: 10 заказов, 6 станков, 55 операций [S7]. В репозиторий стенда включить точную копию исходного файла с URL, исходным commit SHA и SHA-256. При первом импорте workflow проверяет эти размеры; несовпадение останавливает подготовку.

В workflow build-datasets:

1. Прочитать альтернативные станки и длительности.
2. Построить допустимое расписание через OR-Tools CP-SAT: одна выбранная альтернатива на операцию, технологические зависимости, отсутствие пересечений на станке.
3. Минимизировать C0 при лимите 120 секунд, одном потоке и фиксированном seed.
4. Сохранить статус решателя, допустимое решение, нижнюю границу и C0.
5. Проверить решение независимым валидатором.
6. Зафиксировать полученный файл расписания для всей кампании.

Если оптимальность не доказана, использовать допустимое решение и явно указать разрыв с нижней границей. Решатель не запускается заново перед каждым сценарием. Опубликованные примеры OR-Tools описывают ограничения Job Shop и гибкие назначения [S8].

Исходный Mk01 трактовать с неограниченными промежуточными буферами, нулевым транспортным временем и без переналадок, календарей смен и отказов. Эти ограничения добавляются отдельно.

### 8.2. Основная сетка

Пусть A = {0,10; 0,30; 0,50; 0,70; 0,90}, B = {0,05; 0,10; 0,20}.

| Семейство | Конструкция | Число |
|---|---|---:|
| M0 | Без нарушений | 1 |
| M1 | Каждый из 6 станков; начало отказа a × C0, длительность b × C0 для всех a из A и b из B | 90 |
| M2 | Все 15 неупорядоченных пар станков; одинаковое начало и длительность обоих отказов, та же сетка A × B | 225 |
| M3 | Каждая из 55 операций; увеличение работы на 25%, 50% и 100% | 165 |
| **Всего** | **480 нарушений и исходный сценарий** | **481** |

В M3 увеличивается длительность именно выбранной операции на назначенном станке. Изменение сохраняется в её экземпляре данных; задержка не добавляется повторно на каждом временном шаге.

M2 покрывает синхронные парные отказы. Несинхронные отказы и разные длительности не объявлять проверенными этой сеткой.

Каждый сценарий оценить для D/C0 = 1,00; 1,10; 1,25. В DIAGNOSTIC достаточно одной полной траектории на сценарий для оценки всех трёх сроков. При измерении MISSION отдельный D задаёт отдельную точку времени расчёта.

### 8.3. Шаг TSFG и точность

Первый результат использует Δ=0,05: параметры M0–M3 и целочисленное исходное расписание точно представимы на такой сетке. Ровно 481 DIAGNOSTIC-траектория на движок оценивается для трёх D, всего 1 443 исхода миссии. Для общей траектории принять D_diag=1,25C0, предел — 10D_diag; неизвестный полный срок не удовлетворяет приёмке первого результата.

Шаги Δ=1 и 0,25 относятся к последующему исследованию погрешности. Несогласованные входы нельзя молча округлять в точном GRID; сначала требуется спецификация отдельного приблизительного профиля. Эти исследования не входят в критерий завершения первого результата.

Требовать совпадения начала и окончания каждой операции с эталоном при допуске только на представление чисел. При целочисленной шкале требуется точное равенство. Более грубые шаги служат отдельным исследованием погрешности.

Если даже согласованная сетка даёт сдвиг на один шаг из-за порядка обслуживания узлов, это расхождение семантики. Его необходимо устранить либо описать как ограничение приблизительного профиля.

### 8.4. Диагностика каскада

Для каждой задержанной операции записать непосредственную причину ожидания: технологический предшественник, занятый или недоступный станок, плановое начало, дополнительный ресурс либо заполненный буфер.

Для одиночного отказа сформировать цепочку от воздействия к задержанным операциям и конечным заказам. Для парного отказа рассчитать взаимодействие:

I(A,B) = C(A,B) − C(A) − C(B) + C0.

Здесь C — полное время завершения из DIAGNOSTIC. Положительное I означает усиление задержки относительно суммы одиночных эффектов. Дополнительно выявить пары, у которых оба одиночных сценария выполнили задание, а совместный привёл к срыву.

Такое сравнение — вычислительное вмешательство в заданную модель. Оно не доказывает причинность для реального предприятия без проверки модели на фактическом исполнении.

**Выход первого E1:** таблица 481 траектории при Δ=0,05, 1 443 исхода на движок, пооперационное сравнение времён, инварианты, графики сроков, ранжирование ресурсов по §13.1, критические пары и один разобранный каскад. Требуются отсутствие ложного успеха и ложного срыва и точное совпадение времён. Наличие спецификации без исполнений в Actions не означает прохождения E0-core или E1. Отчёт по грубым шагам выпускается позднее отдельно.

## 9. E1X: расширения производственной модели

Каждое расширение получает отдельный идентификатор, исходный сценарий и описание правил. Название «исходный Mk01» к таким данным не применять.

До реализации расширения требуется отдельная спецификация перехода и соответствующий E0-extended. Для буферов определить конкурирующие передачи, внешний склад и освобождение после последней операции; для дополнительного ресурса — прерывание текущей обработки, удержание станка и восстановление; для дробных скоростей — представление работы и допуск. Эти правила не входят в готовую спецификацию GRID и не требуются для первого результата Mk01.

### 9.1. Снижение мощности

Для каждого станка использовать пять моментов начала из E1. Длительность воздействия — 0,20C0, коэффициенты скорости — 0,50; 0,75; 0,90. Получится 6 × 5 × 3 = 90 сценариев.

Оставшаяся работа уменьшается со скоростью действующего коэффициента. Производительность меняет темп обработки, число параллельных операций остаётся равным одному. Проверять сходимость при уменьшении Δ; совпадение на сетке основной серии автоматически на эту серию не распространяется.

### 9.2. Конечные буферы

Основной вариант расширения: отдельный входной буфер каждого станка с вместимостью 1, 2 либо 4 детали. Начальный внешний склад не ограничен.

Завершённая деталь, которую невозможно передать в следующий буфер, остаётся на предыдущем станке и удерживает его. Разделить момент завершения обработки и момент освобождения станка. Деталь в обработке не входит во вместимость входного буфера. При возможности немедленно начать следующую операцию допускается непосредственная передача; порядок из раздела 4 обязателен.

Построить исходное допустимое расписание для каждой конфигурации буферов. Проверить его исполнение без отказов. Конфигурации с исходной блокировкой сохранить как отдельный результат и исключить из утверждений о срыве изначально выполнимого плана.

Сначала повторить M1 на трёх конфигурациях. Полную сетку M1–M3 запускать после прохождения валидации. Все сравнения воздействия относительно исходного сценария выполняются внутри одной конфигурации.

### 9.3. Дефицит дополнительного ресурса

Добавить общий ресурс «наладчик» ёмкостью один, необходимый выбранным операциям на интервале обработки. Список операций закрепить до запуска; использовать первые операции заказов с чётным идентификатором.

Построить новое допустимое исходное расписание с этим ограничением. Задать недоступность наладчика в пяти моментах из E1 на 5%, 10% и 20% нового C0: 15 сценариев.

Эта серия проверит совместное требование станка и другого ресурса. Она также покажет, достаточно ли расширенного состояния TSFG для запрета двойного использования ресурса.

### 9.4. Переналадки и транспорт

Переналадки и транспортные ограничения включить во вторую очередь реализации после основных результатов. До этого явно указывать их отсутствие. Для переналадок потребуется зависимость от пары соседних типов операций; для ограниченного транспорта — отдельный ресурс и правило очередности.

**Мотивация E1X:** исходный Mk01 охватывает только часть заявленного промышленного сценария. Этот этап проверит буферы и дополнительные ограничения без подмены исходного эталона.

## 10. E2: задания до миллиона операций

### 10.1. Размеры и семейства

Основные размеры N: 1 000, 10 000, 100 000 и 1 000 000 операций. Каждый заказ содержит 10 операций; число заказов равно N/10.

Во всех основных экземплярах использовать 200 станков: 10 технологических групп по 20 станков. Заказы разделяют станки и очереди. Размер предприятия в этой серии сохраняется, поэтому увеличение N увеличит также длительность расчётного горизонта. Обе величины должны присутствовать в результатах.

| Семейство | Маршруты и обработка | Проверяемое свойство |
|---|---|---|
| F1: повторяющееся производство | Каждый заказ проходит группы 0…9. Все 20 станков группы допустимы. Работа операции в группе g равна 20 + 4g секундам | Благоприятные условия для объединения однородных операций; сохраняются дискретные экземпляры заказов |
| F2: неоднородное производство | Для каждого заказа случайная перестановка 10 групп. На операции допустимы 3 станка соответствующей группы. Базовая длительность — целое число 20…60 секунд; коэффициенты альтернатив 0,8; 1,0; 1,2 с округлением длительности вверх до секунды | Ограниченная совместимость, разные маршруты и длительности |

Агрегируемость F1 не означает автоматически точного совпадения пооперационного и потокового решения. Проверка дискретного запуска и завершения остаётся обязательной.

F3 со сборкой включить в расширенный набор: два компонента по три последовательные операции, затем сборочная операция и три заключительные операции. Итого 10 операций на заказ; у сборки два предшественника. Это семейство проверяет зависимость от комплектности.

### 10.2. Получение исходного плана

Большое расписание построить детерминированным последовательным назначением по глобально ближайшему допустимому началу:

1. Хранить множество R операций, все технологические предшественники которых уже назначены. Для первой операции заказа в формулу явно входит время поступления материала.
2. Для каждой допустимой пары (i,m), i∈R, вычислить start(i,m)=max(r(i), max plan_end(P(i)), tail_end(m)); для отсутствующих предшественников и пустого станка использовать 0.
3. Вычислить finish(i,m)=start(i,m)+p(i,m).
4. Среди всех пар выбрать лексикографический минимум (start, finish, job_id, operation_id, machine_id). Приоритет готовности применяется до идентификаторов, а не только при выборе станка для уже выбранного заказа.
5. Назначить пару, сохранить s0 и плановое окончание, добавить i в конец очереди m, обновить tail_end и множество R. Повторять до назначения всех операций.

Это нормативный порядок выбора, а не требование заново перечислять все пары после каждого назначения. Допускается индексированная реализация. Например, хранить лучший вариант каждой готовой операции в куче и лениво пересчитывать ключ при извлечении: доступность станков только сдвигается вперёд, поэтому старые ключи являются нижними оценками; выбирать операцию можно лишь после подтверждения актуального минимального ключа. Соответствие простому независимому перечислению проверяется на малых наборах в Actions. Время и число пересчётов генератора сохраняются отдельно.

Обязательный тест генератора: один станок, A с меньшим ID, r(A)=100, p(A)=10; B с большим ID, r(B)=0, p(B)=10. Ожидается B:[0,10), A:[100,110), C0=110. Вариант A:[100,110), B:[110,120) не проходит тест. Дополнительно проверяется, что малая операция с двумя альтернативами выбирается по указанному общему ключу, а не только по минимальному окончанию.

Генератор не заполняет ранее пропущенные свободные интервалы и не обещает оптимальный план. После построения независимый валидатор проверяет весь план, включая поступления. Сохранить C0, плановые простои, загрузку станков и нижние оценки длительности по критическому технологическому пути и суммарной работе.

Этот план пригоден для проверки исполнения. Качество оптимизации относительно BFG APS по нему не оценивать. Время построения плана раскрыть отдельно.

### 10.3. Плотность событий

Для каждого семейства подготовить два профиля:

- **DENSE:** все заказы доступны с момента 0.
- **SPARSE:** сначала определить C_dense для того же состава заказов; затем распределить моменты поступления равномерно по целым секундам интервала [0, 3C_dense] и построить новое расписание.

SPARSE проверяет изменение загрузки при растянутых равномерных поступлениях. Он не гарантирует длительных промежутков, когда во всей системе нет работы. DENSE и SPARSE остаются двумя профилями основной матрицы.

Для проверки именно пустых интервалов добавить отдельный профиль **BURST**, вне основной матрицы и критерия H3 версии 1.1. Разделить заказы по возрастанию ID на четыре последовательные группы, размеры которых отличаются не более чем на один заказ; лишние заказы относятся к первым группам. Для каждой группы независимо построить расписание при поступлении в 0 и получить C_b. Задать G=max(1,ceil(C_dense)) секунд, r_1=0, r_(b+1)=r_b+C_b+G; все заказы группы b поступают в r_b. На этих поступлениях снова применить общий генератор §10.2. Валидатор исходного сценария подтверждает пустые промежутки длиной не менее G между группами. При отказах промежутки могут сократиться; это фиксируется в результате.

BURST использует те же составы заказов и 4 размера × 2 семейства × 3 seed, всего 24 дополнительных экземпляра. Он проверяет накладные расходы GRID на пустом времени и будущие отдельные варианты пропуска. Нельзя включать пропуск интервалов в GRID без нового algorithm_id.

Загрузку вычислять по фактическому плану. Для всех профилей записывать долю времени без обработки во всей системе, наибольший такой промежуток и интервалы между событиями. Названия профилей не заменяют измерений.

### 10.4. Матрица исходных данных

4 размера × 2 семейства × 2 профиля поступления × 3 seed = **48 экземпляров**.

Проверка корректности на каждом экземпляре: исходный сценарий и первые 10 сценариев из общей серии. Для публикуемого измерения скорости каждый дополнительно используемый сценарий также проходит сопоставление выходных показателей. Проверка может выполняться отдельным запуском вне измеряемого интервала, но на том же входе.

Отдельная дополнительная серия с ростом оборудования:

| N | Станков | Станков на группу |
|---:|---:|---:|
| 10 000 | 20 | 2 |
| 100 000 | 200 | 20 |
| 1 000 000 | 2 000 | 200 |

В этой серии F2 ограничить двумя альтернативами во всех размерах. Она проверит рост системы при приблизительно постоянной работе на станок. Результаты не смешивать с основной серией на 200 станках.

### 10.5. Сценарии для больших заданий

Сформировать один список из 1 000 сценариев для каждого экземпляра. Подсписки K = 1, 10, 100, 1 000 являются префиксами этого списка.

Чередовать по scenario_id четыре семейства: одиночный отказ, парный отказ, увеличение работы одной операции, отказ пяти станков общей технологической группы. Таким образом полный список содержит по 250 сценариев каждого семейства.

Параметры выбирать детерминированным генератором:

- начало отказа: от 0,10C0 до 0,90C0;
- длительность: 0,01C0, 0,05C0 или 0,10C0;
- все неотрицательные границы интервалов округлять до целых секунд по floor(x+0,5) при создании общего файла;
- для задержки операции добавить 25%, 50% либо 100% работы с округлением вверх до секунды;
- станки в одном воздействии выбирать без повторений;
- идентификатор операции выбирать из всего задания.

Одинаковые воздействия передать всем движкам. Сценарии, попавшие на незанятый станок, сохранять: они проверяют отсутствие ложного каскада. Отдельно отмечать долю воздействий, которые пересеклись с фактической обработкой.

Этот список задаёт нагрузку и покрытие сценариев. Частоты выбора семейств не обозначают эксплуатационные вероятности.

### 10.6. Шаг пооперационного TSFG

Основной шаг E2 — 1 секунда. Входы основной серии и исходный план целочисленны; длительности положительны. Проверить точное воспроизведение временных отметок на таком профиле.

На калибровочных экземплярах позднее выполнить дополнительные расчёты с Δ=0,25 и 5 секунд с подходящей целочисленной шкалой хранения. Шаг 5 секунд допускается только после определения отдельного приблизительного профиля для несогласованных входов и публикуется вместе с погрешностью. Обработка событий внутри шага требует отдельного algorithm_id, описания алгоритма и счётчика внутренних событий.

## 11. E3: агрегация и точность

### 11.1. Представления

| Представление | Состояние | Ожидаемое ограничение |
|---|---|---|
| G0 | Каждая операция и её очередь сохранены | Наибольшая детализация |
| G1 | Группы операций с одинаковыми правилами обработки; сохранены необходимые индивидуальные сроки и границы групп | Выигрыш зависит от числа различимых групп |
| G2 | Объёмы материала по типам и суммарные мощности допустимых пулов | Индивидуальный порядок может быть утрачен; требуется оценка ошибки |

Для каждого объединения указать, какие поля одинаковы: набор допустимых ресурсов, работа, последовательность стадий, доступность материалов, срок и правила очередности. Если эти условия не выполнены, точную эквивалентность не заявлять.

Приблизительное объединение неоднородных операций разрешено в G2 как отдельный опыт. Способ усреднения и все отброшенные ограничения сохранить в описании.

### 11.2. Сравниваемые результаты

Для G0 сравнивать пооперационные времена и состояния с учётом режима остановки. Для G1 и G2 сравнивать только заявленные поддерживаемые поля, включая выпуск, сроки при их доступности, очереди, исходы миссии и порядок критичности ресурсов. Контракт результатов и класс точности выбираются до запуска; отсутствие индивидуальных состояний нельзя скрыть агрегированным совпадением.

Если представление не выдаёт сроки отдельных заказов, это поле получает статус UNSUPPORTED. Число операций исходного задания при этом сохраняется, но формулировка результата должна указывать агрегированное представление.

Для функционально ограниченного сравнения G2 с DES использовать одинаковый запрошенный выход, например общий выпуск к D. У DES отключить ненужное подробное журналирование. Наличие внутри DES индивидуальных состояний отразить в памяти и времени.

### 11.3. Классы точности по горизонту и выходу

Вместо неоднозначных EXACT и APPROX-1 версии 1.0 применяются следующие профили и служебные статусы. Класс указывается вместе с output_profile; инварианты модели обязательны во всех случаях.

| Класс / статус | Режим и требование |
|---|---|
| EXACT-MISSION | MISSION, SCHEDULE: совпадают известные начала и окончания, статусы и остатки всех операций к D, выпуск и оба вида классификации миссии. Для FULL дополнительно точно совпадают очереди и интегралы на [0,D] |
| EXACT-DIAGNOSTIC | DIAGNOSTIC: все обязательные операции завершены до предела; совпадают все индивидуальные начала и окончания и исходы для заданных D; для FULL совпадают метрики на одинаковых горизонтах |
| APPROX-MISSION-1 | MISSION, AGG-MISSION: ошибка выпуска и числа незавершённых заказов ≤1% числа обязательных заказов J; ошибка очереди к D и её максимума для каждого станка ≤1% J; относительная ошибка интеграла НЗП на [0,D] ≤5%; нет ложного успеха. Ложные срывы раскрываются отдельным числом и долей |
| APPROX-DIAGNOSTIC-1 | Условия APPROX-MISSION-1 плюс известное полное завершение обоих расчётов и максимальная ошибка общего срока ≤1% C0 |
| OUTSIDE | Нарушено требование заявленного класса либо обязательное для него поле UNSUPPORTED |
| CENSORED | Полный срок неизвестен из-за остановки на горизонте; ошибка полного срока не вычисляется и диагностический класс не присваивается |

Пороги приблизительных профилей — рабочие требования исследования. Применимость к конкретному производству зависит от допустимой ошибки заказчика. Для сборки и иной размерности очередей до запуска требуется отдельный контракт единиц и нормировки; пороги цепочной серии автоматически не переносятся.

Если профиль поддерживает только выпуск, его можно измерять как функционально ограниченный опыт, но он не проходит APPROX-MISSION-1 без остальных обязательных метрик. EXACT-MISSION не требует знания будущего полного срока, а EXACT-DIAGNOSTIC не может быть принят по двум одинаково обрезанным траекториям.

Если эталонный интеграл равен нулю, относительную ошибку не рассчитывать: раскрыть абсолютное отклонение, а класс считать выполненным только при нулевом отклонении.

Все ошибки оцениваются по каждому сценарию, после чего берётся максимум по объявленному набору. Сравнение min(C,D) или min(C,10D) вместо полного срока запрещено. Незавершённый DIAGNOSTIC может отдельно пройти EXACT-MISSION на известном горизонте, но не получает статуса полного временного совпадения.

Для сроков рядом с D публиковать отдельную таблицу. Исключать пограничные случаи ради улучшения доли совпадений запрещено.

Представить зависимость «время — ошибка», число исходных операций и размер агрегированного состояния. Публиковать также неблагоприятные для агрегации результаты F2 и SPARSE.

| T_workflow | Время workflow с подготовкой и передачей артефактов; отдельный эксплуатационный показатель |

Ожидание свободного runner, скачивание зависимостей и сборка не входят в T_batch. В отчёте они остаются частью T_workflow.

Одинаково определить объём выходных результатов. Подготовку графа TSFG нельзя исключить из полного времени, если аналогичная подготовка эталона включена. Кеширование неизменной модели разрешено всем движкам; влияние кеширования показать отдельно.

Основной выход для сравнения TSFG-OP, DES-REF и DAG-REF — SCHEDULE в MISSION: одинаковые индивидуальные времена и состояния к D, выпуск и исход задания по §6.3. Проверка инвариантов и дополнительная подробная диагностика могут выполняться вне таймера на тех же входах. FULL — самостоятельная дополнительная серия; для DAG стоимость восстановления очередей и интегралов по временам включается в её замер. Выходные профили нельзя смешивать в одном коэффициенте.

Основной коэффициент на одной VM для двух повторов каждого движка:

S_REF(K) = sqrt((T_batch_REF,1(K) × T_batch_REF,2(K)) / (T_batch_TSFG,1(K) × T_batch_TSFG,2(K))), REF∈{DES,DAG}.

Аналогично вычислить S_total_REF из T_total самостоятельных процессов. Каждое исходное время сохранить. Оба повторения должны закончиться корректно; один завершённый повтор не заменяет пару. Точки с приблизительным агрегированным выходом относятся к H4, а не к основной H3 точного пооперационного профиля.

### 12.2. Парные замеры в одном задании Actions

Каждая точка matrix содержит один экземпляр данных, одну конфигурацию TSFG, один output_profile, режим остановки и самостоятельное K. Внутри одного job все применимые движки выполняются последовательно на одной VM. Основная серия включает TSFG-OP, DES-REF и DAG-REF.

Для трёх движков A=TSFG, B=DES, C=DAG выбрать одну из шести перестановок по закреплённому seed и выполнить её, затем обратный порядок: например A–B–C–C–B–A. Каждый движок получает два запуска; коэффициенты относительно DES и DAG вычисляются из этих шести времён. Для расширений, где DAG неприменим, использовать A–B–B–A или B–A–A–B и явное поле причины отсутствия DAG. Основная серия не может исключить применимый DAG.

Каждый измеряемый запуск начинает новый процесс. Общий короткий прогрев файловой системы и загрузки кода выполнять одинаково, вне таймера. Для варианта с JVM дополнительно определить и раскрыть прогрев JIT.

Для основных публикуемых точек повторить workflow на трёх независимо выделенных runner. Внутри каждой попытки вычислить парное отношение времён. Между машинами сравнивать отношения, сохраняя CPU model и версию образа; простое отношение времени TSFG на одной машине к DES на другой запрещено.

Если run не прошёл проверку выходных показателей, время сохранить со статусом INCORRECT. В сводку корректного ускорения его не включать.

### 12.3. Ограничения ресурсов

Основной профиль для всех сравниваемых движков:

- GitHub-hosted Ubuntu 24.04, x64;
- один выделенный процессу логический CPU и один вычислительный поток;
- предел памяти контейнера 4 GiB, без дополнительного swap;
- одинаковый образ инструментов, параметры оптимизации и ограничения;
- без одновременного выполнения другого измеряемого движка в том же job;
- отключённые подробные логи одинакового уровня;
- фиксированный набор обязательных метрик.

Выбранные 4 GiB оставляют запас операционной системе стандартного runner. Отдельную серию с большим лимитом разрешить только как новый профиль, если стандартный исполнитель располагает достаточной памятью.

Документация GitHub на дату подготовки указала для стандартных Linux x64 runner 4 CPU и 16 GB RAM в публичных репозиториях, 2 CPU и 8 GB RAM в закрытых; диск — 14 GB [S10]. Поэтому публичность репозитория и фактические ограничения входят в manifest. Видимость репозитория этим планом не изменяется.

Ubuntu 24.04 фиксирует семейство ОС, но не неизменный образ виртуальной машины. Сохранить ImageVersion, ядро, модель CPU, доступную память, сведения об ограничениях контейнера и версии инструментов. Образ исследовательских инструментов фиксировать по digest; он не фиксирует физический CPU.

### 12.4. Лимиты и незавершённые измерения

Начальный лимит одного измеряемого вызова — 300 секунд. Таймер относится ко всему самостоятельному процессу, включая подготовку, максимум K сценариев и запись результатов. Для H3 необходим отдельный процесс с K=100; K=1000 запускается отдельно. Контрольные точки 1, 10, 100, 1000, меньшие заявленного K, записываются как T_prefix(k;K). Они не подменяют самостоятельные T_batch(k) и T_total(k). Время сброса между сценариями включается в T_batch.

При TIMEOUT сохранять число завершённых сценариев и достигнутые контрольные точки. Нельзя объявлять время завершения всей серии равным лимиту. Для одного завершённого и одного незавершённого самостоятельного процесса можно публиковать границу отношения полного времени, например S_total>L/T при таймауте эталона. Граница для T_batch допустима лишь при отдельно измеренной нижней границе времени серии; общий лимит процесса не является такой границей. Эти границы не участвуют в принятии H3 версии 1.1. Когда оба процесса не завершились, конечный коэффициент из лимитов не выводится.

MEMORY_LIMIT учитывать отдельно от TIMEOUT. Рост масштаба после превышения памяти не объявлять корректно измеренным.

После первого результата Mk01 выполнить самостоятельный K=10 для всех 48 экземпляров. Затем K=100 для экземпляров N=100 000 и N=1 000 000, по трём runner_round. K=1000 — дополнительный самостоятельный прогон после оценки затрат. BURST и остальные размеры с длинными сериями получают отдельные кампании.

Предельная длительность одного benchmark job — 60 минут, включая сбор служебных данных и передачу артефактов. Шесть вызовов по 300 секунд занимают не более 30 минут и оставляют запас для подготовки. Проверку корректности вынести в отдельный job с собственным пределом; допуск сохраняется отдельно для конкретных входов, output_profile и K. Проверенный префикс может подтвердить корректность соответствующего самостоятельного K, но не заменить его измерение. Превышение лимита проверки нужных 100 сценариев означает отсутствие допуска этой точки H3.

### 12.5. Вычислимый критерий H3

Оценивать отдельно четыре заранее заданные области: F1/DENSE, F1/SPARSE, F2/DENSE, F2/SPARSE.

Решение вычислять отдельно для каждого эталона REF∈{DES,DAG}, каждой области и каждого размера N∈{100 000,1 000 000}; имена результатов — H3-DES и H3-DAG. Основной профиль — точный TSFG-OP, MISSION, SCHEDULE, самостоятельное K=100. H1 и H2 должны быть пройдены, все 100 сценариев каждой точки — допущены как EXACT-MISSION/SCHEDULE.

Для фиксированных REF, области и N требуется полный набор из 3 seed данных × 3 runner_round, всего 9 точек. В каждой точке оба повтора TSFG и оба повтора выбранного эталона должны закончиться со статусом OK и пройти проверку. Запуск на каждой VM включает также второй применимый эталон, но решения H3-DES и H3-DAG независимы.

Пусть S_(d,r) — отношение §12.1 для seed d и runner_round r. Определить:

- G_r = (S_(101,r) × S_(102,r) × S_(103,r))^(1/3).
- G = (произведение S_(d,r) по всем 9 точкам)^(1/9).

Статус SUPPORTED присваивается для данного размера, если G≥2 и каждый G_r>1. Если все 9 точек корректны и завершены, но пороги не выполнены, статус NOT_SUPPORTED. Если хотя бы одной обязательной завершённой корректной точки нет, статус INSUFFICIENT_COMPLETED; H3 остаётся неподтверждённой, без усреднения по оставшимся удобным точкам. Отдельно публикуются причины: таймаут, ошибка, отсутствие проверки или запуска.

H3 относительно данного эталона на диапазоне подтверждена только при SUPPORTED отдельно на обоих размерах. Объединять размеры в одно среднее для принятия запрещено. Утверждение о преимуществе перед обоими эталонами требует выполнения обоих решений; выигрыш только у DES называется именно выигрышем у DES.

Для позиционирования полного пользовательского расчёта аналогично вычислить G_total и G_total,r по самостоятельным T_total(100) и потребовать G_total>1 и каждый G_total,r>1 на обоих размерах. Ускорение полного расчёта «не менее 2» можно утверждать лишь при G_total≥2, а не переносить на него порог для T_batch.

K = 1 000 служит дополнительной целью массового анализа. Ускорение в 10 раз можно принять как желаемый инженерный ориентир; оно не требуется для признания H3.

Результат одной области нельзя распространять на остальные. Показывать все индивидуальные отношения, медиану и диапазон по независимым runner. Два повтора в одной VM не считаются двумя независимыми VM. Малое число исходных экземпляров не даёт основания для универсального статистического вывода обо всех производствах. Таймауты и границы отношений показываются рядом с решением, но не заменяют завершённые точки в формулах этой версии.

Если DAG-REF быстрее TSFG в поддерживаемой постановке, указать это рядом с ускорением относительно DES. Такой результат ограничивает практическую ценность выигрыша над событийной реализацией для простых фиксированных расписаний.

## 13. E4: оценка резервов и вероятности выполнения

### 13.1. Изменения производства

До оценки резервов зафиксировать ранжирование. Для каждого станка m выполнить одинаковые 15 одиночных отказов по A×B из §8.2 на соответствующем исходном плане; для больших наборов границы однократно округляются до секунды по правилам генератора. Это отдельная сбалансированная диагностическая серия, а не выборка случайно чаще затронутых станков из E2. Её стоимость учитывается отдельно.

Для известных полных сроков определить R_m=(1/15)Σ_(a,b)((C_(m,a,b)−C0)/C0), дополнительный показатель F_m — число срывов при D=1,10C0 из этих 15. Ранжировать по убыванию R_m, затем F_m, затем по возрастанию machine_id. Точные равенства разрешаются ID; для целочисленных времён суммы задержек сравниваются без округления плавающей точки. Если необходимый полный срок неизвестен или расчёт некорректен, ранжирование не допущено; предел остановки не подставляется.

Выбрать три первых ресурса как T. Из оставшихся выбрать три ресурса с наименьшими R_m, затем F_m, затем ID как контроль B; группы не пересекаются. При числе ресурсов меньше шести данная процедура неприменима. На Mk01 она использует ровно M1, а не результаты M2/M3. Версия ранжирования, группы и параметры вмешательств закрепляются до оценочной серии.

После этого исследовать кандидатов:

| Изменение | Фиксируемое правило | Ограничение интерпретации |
|---|---|---|
| Резервный станок | Один дополнительный ресурс, совместимый с выбранным основным станком | Дополнительную мощность и время доступности включить в описание затрат |
| Альтернативное назначение | Перевод ещё не начатой операции на допустимый свободный станок при отказе основного | Правило выбора и порядок изменения очередей совпадают у TSFG и DES |
| Увеличение скорости | +10% скорости выбранного станка | Это изменение паспортной мощности, отдельное от восстановления после отказа |
| Расширение буфера | +2 места в выбранном конечном накопителе | Проверять только в серии с конечными буферами |
| Перераспределение временного резерва | Новый допустимый исходный план с прежним D и прежними внешними ограничениями | Сохранить оба расписания; перестановка должна пройти независимую проверку |

Для резервного станка незавершённые операции остаются на основном. Готовую ещё не начатую операцию переводить только при доступном совместимом резерве; при равенстве кандидатов выбрать минимальное ожидаемое окончание, затем идентификатор. Удаление из исходной очереди и вставку в очередь резерва зафиксировать в журнале.

Сравнить кандидатов на T и B. Основное вмешательство для принятия H5 — увеличение скорости одного выбранного станка на 10%, шесть самостоятельных конфигураций при одинаковом бюджете относительного прироста мощности одного станка. Его реализация требует прошедшего E0-extended для дробной скорости. Резервный станок, буферы и переназначения остаются отдельными опытами; нельзя выбрать лучший их результат после оценки и подменить им основной критерий H5. Глобальную оптимальность среди всех изменений не заявлять.

Срок D, объём задания и сценарии внешних воздействий сохраняются. Если исходный план изменён, отдельно раскрыть это изменение. Стоимость разных видов резервов в рублях не рассчитывать без входных цен. Сравнивать эффект внутри сопоставимых бюджетов: число дополнительных станков, машино-часы или места хранения.

### 13.2. Измерение эффекта

Для детерминированной сетки:

- число сценариев, в которых срыв устранён;
- число новых срывов;
- изменение выпуска к D;
- изменение позднего завершения и незавершённого производства;
- добавленные ресурсы.

Доля срывов в такой сетке характеризует набор воздействий. Она не оценивает эксплуатационную вероятность.

Детерминированную проверку Mk01 выполнять на M2 и M3, не использованных для определения R_m. Она описывает полезность на этой сетке. Окончательный H5 оценивать отдельно для заранее выбранных F1/DENSE и F2/DENSE, N=100 000, dataset seed=101, на новой стохастической серии §13.3.

Для каждого независимого сценария s обозначить бинарный успех исходной системы y0(s), успех после увеличения скорости ресурса m — ym(s). Определить e_T(s)=(1/3)Σ_(m∈T)(ym(s)−y0(s)), e_B(s) аналогично и d(s)=e_T(s)−e_B(s). Основные показатели — средние e_T и d. Один сценарий со всеми семью исходами образует единую парную запись; строки нельзя независимо перемешивать между конфигурациями.

Для каждого показателя построить парный percentile bootstrap-интервал: 10 000 выборок по 1 000 сценарных записей с возвращением, квантили 0,025 и 0,975, метод квантиля linear, именованный поток seed `h5_bootstrap` по §6.2. H5 для данного экземпляра подтверждается, только если нижние границы обоих интервалов строго больше нуля, все сравниваемые расчёты корректны и затраты соблюдены. При интервале, включающем ноль, H5 неподтверждена; при незавершённых обязательных сценариях оценка недостаточна. Результаты двух семейств не объединяются для принятия. Интервалы характеризуют исследовательский профиль отказов, а не неизвестное производство.

### 13.3. Отдельная стохастическая серия

Начать с N=100 000 и экземпляров F1/DENSE и F2/DENSE, dataset seed=101. Подготовить 1 000 независимых сценариев на экземпляр с purpose `h5_evaluation`, не участвовавших в выборе вмешательств. Эти сценарии одинаковы для исходной конфигурации и шести основных вмешательств. До запуска сохранить список T/B и хеш конфигураций; менять его по оценочным результатам нельзя.

Исследовательский профиль отказов, без претензии на статистику предприятия:

- всё оборудование работоспособно в момент 0;
- интервалы работоспособности каждого станка имеют экспоненциальное распределение со средним 10D;
- длительность ремонта равномерна на [0,01D; 0,03D];
- время относится к календарному времени;
- каждый станок проходит чередование работоспособности и ремонта;
- дополнительные общие отказы группы включаются отдельной серией: события пуассоновского процесса со средним интервалом 2D, пять станков одной заранее указанной группы, ремонт длительностью 0,02D;
- индивидуальные процессы генерируются независимо от общего фактора; фактическая недоступность — объединение интервалов.

Все интервалы сгенерировать до запуска движков и сохранить. Для этой серии на синтетических данных округлить неотрицательные границы до ближайшей секунды по floor(x+0,5) единожды при подготовке файла; минимальная длительность ремонта — одна секунда. Это определяет дискретизированный исследовательский профиль. Все участники получают одинаковые интервалы.

Для нового резервного оборудования сгенерировать отдельные отказы. Общая причина воздействует на резерв, если он принадлежит той же группе. Сравнение не должно неявно считать добавленный станок безотказным.

Для вероятности выполнения использовать долю успешных миссий и 95%-й интервал Уилсона. При 1 000 независимых сценариях максимальная полуширина такого интервала составляет приблизительно 3,1 процентного пункта. Более узкие интервалы не обещать заранее.

Эффект вмешательства оценивать попарно на одинаковых сценариях. Для разности вероятностей использовать парный интервал; при проверке изменения бинарного исхода допустим точный критерий Мак-Немара. Эти методы уже указаны в отчёте TSFG [S1]. Выбор кандидата и окончательную оценку выполнять на разных наборах.

Нулевое число ложных безопасных исходов на n независимых сценариях не доказывает нулевой риск ошибки. При биномиальной постановке односторонняя 95%-я верхняя граница равна 1 − 0,05^(1/n). На детерминированную сетку Mk01 такой вероятностный вывод не распространяется.

## 14. Реализация исключительно в GitHub Actions

### 14.1. Правило исполнения

Все исполняемые этапы запускаются workflow в GitHub. Запрет распространяется на локальные компиляцию, тесты, генерацию больших данных, профилирование, моделирование и подготовку итоговых графиков.

Редактирование исходных файлов и документации допускается без исполнения. План не требует публикации закрытого кода, изменения видимости репозитория или переноса проекта в другую организацию.

Основной вариант использует GitHub-hosted runners. Self-hosted исполнители и внешние вычислительные сервисы в протокол не входят.

### 14.2. Предлагаемая структура репозитория

| Каталог | Содержимое |
|---|---|
| .github/workflows | Точки входа и повторно используемые workflow |
| protocol | Этот документ, нормативная спецификация TSFG-OP-GRID, версии правил и классы точности |
| schemas | Схемы данных, сценариев и результатов |
| fixtures/mk01 | Зафиксированный исходный экземпляр и сведения о происхождении |
| generators | Генераторы заданий, расписаний и внешних воздействий |
| engines/tsfg_op | Пооперационный профиль TSFG |
| engines/tsfg_agg | Варианты агрегации |
| engines/des_ref | Независимый событийный эталон |
| references | DAG-REF и SimPy-REF |
| validation | Проверка расписаний, инвариантов и согласия результатов |
| benchmark | Запуск процессов, лимиты, таймеры и сбор сведений о среде |
| analysis | Сводки, таблицы, графики и отчёты |
| configs | Версионированные параметры всех серий |
| containers | Воспроизводимое окружение инструментов |

Большие сгенерированные данные не включать в обычную историю Git. Передавать их между job через артефакты; закреплённые наборы архивировать вместе с manifest.

### 14.3. Workflow и порядок выполнения

| Workflow | Запуск | Содержание | Артефакты |
|---|---|---|---|
| ci.yml | pull_request и push | Сборка, проверка схем, E0-core, чтение Mk01 и малая проверка согласия; E0-extended для реализуемого расширения | Логи, результаты тестов |
| build-datasets.yml | workflow_call из кампании | Импорт Mk01 или генерация набора, исходное расписание, валидатор | Входы и manifest |
| validate.yml | workflow_call | E1 или проверка выходов выбранной большой серии | Инварианты, расхождения, статус допуска |
| benchmark.yml | workflow_call | Шесть последовательных замеров TSFG/DES/DAG на одной VM для экземпляра, конфигурации, выхода и самостоятельного K | timings, metrics, environment, статусы |
| experiment.yml | workflow_dispatch | Проверка параметров, подготовка matrix, зависимостей и всей кампании | Manifest кампании и ссылки на результаты |
| report.yml | workflow_call | Сбор результатов всех обязательных точек, таблицы и графики | report.md, report.html, таблицы, рисунки |
| archive-results.yml | отдельный workflow_dispatch | Закрепление выбранной завершённой кампании в GitHub Release | Снимок протокола, manifest, входы и результаты |

Логические зависимости основной серии: спецификация → сборка и E0-core → подготовка данных → E1/валидация → замеры → отчёт. Для расширения перед его валидацией требуется своя спецификация и E0-extended. Ошибка корректности останавливает публикацию коэффициента ускорения для затронутой точки. Отчёт по ошибке всё равно формируется.

Сборку выполнять один раз на commit. Точный исполняемый файл, digest окружения и входные файлы передавать зависимым job. Каждый job проверяет контрольные суммы.

### 14.4. Параметры ручного запуска

| Вход experiment.yml | Значения и назначение |
|---|---|
| suite | mk01, mk01-extended, scale-screen, scale-main, scale-burst, scale-extra, aggregation, reserves, stochastic |
| protocol_version | Версия правил и порогов |
| dataset_shard | Номер части предварительно сформированного списка экземпляров |
| scenario_limit | 1, 10, 100 либо 1000 для больших серий; scale-main требует самостоятельное 100; mk01 всегда выполняет 481 сценарий, ограничение к нему не применяется |
| representation | op, agg-g1 либо agg-g2 |
| algorithm_id | tsfg-op-grid-v1.1; остальные варианты — только после отдельной спецификации и регистрации |
| output_profile | SCHEDULE, FULL, AGG-MISSION; основная H3 использует SCHEDULE |
| mode | MISSION либо DIAGNOSTIC; mk01 использует DIAGNOSTIC с оценкой трёх D |
| runner_round | 1, 2 или 3 для независимых выделений VM |
| process_time_limit_s | По умолчанию 300 на самостоятельный измеряемый процесс, включая всю серию; изменение создаёт новый профиль |

Операционный способ запуска: вкладка Actions → experiment → Run workflow → выбор ветви с зафиксированным протоколом и перечисленных параметров. Все шаги выполняются внутри GitHub.

Для доступности ручного запуска файл experiment.yml должен присутствовать в основной ветви репозитория. Разработку и проверки изменений вести через ветви и pull request; публикуемые кампании закреплять за конкретным commit.

Commit кода получать из фактического workflow и сохранять. Произвольные строки входов не подставлять в shell как команды. Конфигурации выбирать из разрешённого списка.

### 14.5. Matrix и пределы

Основной список из 48 экземпляров разделить на части максимум по 12 benchmark job. В одном job TSFG, DES и применимый DAG выполняются последовательно; разделение движков на разные элементы matrix запрещено для основного сравнения. Дополнительные 24 экземпляра BURST входят в самостоятельные части и не изменяют знаменатель основной матрицы.

Для matrix задать max-parallel = 2 и fail-fast = false. Отдельные независимые job могут работать параллельно; в одном job измеряемые процессы не конкурируют.

Три runner_round запускаются отдельными попытками кампании на тех же commit и входах. Сводка группирует их по идентификатору эксперимента и fingerprint конфигурации.

GitHub документировал предел 256 job в одной matrix и 6 часов на GitHub-hosted job [S11]. Протокол использует меньшие собственные пределы. Расширение списка параметров выполняется через дополнительные части, без скрытого усечения matrix.

### 14.6. Среда и зависимости

- Использовать ubuntu-24.04 вместо плавающего ubuntu-latest.
- Зафиксировать окружение инструментов по digest образа; сохранить lock-файлы Python и версии компилятора.
- Внешние actions закрепить полными commit SHA при реализации workflow.
- Кешировать зависимости и сборку по точному ключу версии; результаты измерений кешем не подменять.
- Сборку и скачивание данных завершить до начала таймера.
- Включить ограничение памяти и CPU на уровне контейнера; сохранить подтверждение фактических ограничений.
- На каждый запуск записать разрешённый набор CPU, число потоков библиотек и настройки оптимизации.
- Изменение контейнера, флагов или алгоритма считать новым вариантом реализации.

Общие workflow используют минимально необходимые права чтения и работы с артефактами. Право записи релиза требуется только archive-results.yml. Доступ к закрытому исходному TSFG хранить в GitHub Secrets или штатном доступе репозитория; секреты не включать в артефакты.

### 14.7. Сохранение после ошибок

Шаг загрузки частичных результатов выполняется с условием always(). Результаты записываются после каждого завершённого сценария и контрольной точки.

Отдельно различать отказ инфраструктуры, превышение лимита и нарушение модели. Автоматический повтор допустим при INFRA_FAILURE, при этом исходная попытка остаётся в журнале. Повтор медленного корректного замера до получения удобного времени запрещён.

Отчёт содержит ожидаемый список точек. Отсутствующая точка отображается как MISSING. Отчёт не объявляет кампанию завершённой по одному наличию файлов.

### 14.8. Артефакты и срок хранения

Задать retention-days = 90 в пределах политики репозитория. Если политика допускает меньше, сохранить фактический срок в отчёте и закрепить итоговую кампанию архивным workflow. GitHub поддерживает передачу результатов между job через workflow artifacts [S12].

Артефакт точки должен содержать manifest.json, environment.json, metrics.jsonl, timings.csv, validation.json и сведения о входах. Трассы хранить выборочно по правилам раздела 6.

До окончания срока хранения итоговые результаты и входы выбранной кампании закрепить в GitHub Release. Для воспроизведения сохранить также commit генератора, образ окружения и точные параметры. Сам по себе seed без версии генератора недостаточен.

Результаты пока не запускались и не публиковались. Этот раздел определяет будущую реализацию workflow.

## 15. Порядок разработки и контрольные результаты

Первый результат ограничен спецификацией, E0-core и Mk01. Прежние оценки версии 1.0 — 15–27 дней на всю программу и 10–18 на P0–P3 — не считаются актуальной сметой версии 1.1. Трудоёмкость следующих этапов пересчитывается после завершения E1 по фактической сложности ядра, эталонов и Actions. Доступ к продуктам поставщиков оценивается отдельно.

| Этап | Работа | Условие завершения |
|---|---|---|
| P0 | Спецификация GRID, контракты, происхождение S1; репозиторий, окружение и workflow | Спецификация закреплена за версией; первый workflow сохранил manifest |
| P1 | TSFG-OP-GRID, независимые DES/DAG и малый SimPy | Все E0-core пройдены в Actions |
| P2 | Mk01, одно зафиксированное расписание, Δ=0,05 и E1 | 481 полная траектория, 1 443 исхода на движок; точное согласие и отчёт |
| После первого результата | Пересмотр сметы, генератор E2, самостоятельные K=10 и K=100 | Новая смета и бюджет; далее результаты по обоим размерам и обоим эталонам |
| Последующие серии | BURST, K=1000, приблизительные профили, E0-extended/E1X, агрегация и резервы | Отдельные спецификации, допуски, измерения и отчёты |

Первый результат завершён только при наличии ссылок на успешные Actions и проверяемых артефактов P0–P2. Редактирование протокола и спецификации не заменяет эти исполнения.

### 15.1. Последовательность изменений

1. **PR 1:** нормативная спецификация GRID, структура репозитория, контракты, запрет локальных экспериментальных запусков, workflow сборки и артефактов.
2. **PR 2:** независимые движки и E0-core; результатом проверки служат ссылки на Actions.
3. **PR 3:** Mk01 и первый E1; зафиксированное расписание и полный отчёт. Здесь заканчивается первый результат и пересчитывается смета.
4. **PR 4:** генератор E2 с тестом позднего поступления, DENSE/SPARSE и отдельный BURST; валидация пооперационных результатов.
5. **PR 5:** замеры TSFG/DES/DAG, самостоятельные K=10 и K=100, вычисление H3 и отчёт; дополнительный K=1000 после оценки затрат.
6. **PR 6:** спецификации расширений, E0-extended, конечные буферы, дополнительные ресурсы и агрегация.

Изменение исходного кода проходит CI в GitHub. В PR указывать workflow run и отличие от предыдущего результата. Рабочая станция не используется для воспроизведения тестов или ускоренного обхода неудачного workflow.

### 15.2. Переход между размерами

Порядок: спецификация GRID → E0-core → Mk01 → пересмотр сметы → 1 000 → 10 000 → 100 000 → 1 000 000 операций. E0-extended вводится перед соответствующим расширением, не перед основным Mk01.

Перед увеличением размера проверить:

- завершённость входного набора и допустимость исходного плана;
- согласие выходов;
- отсутствие нарушений инвариантов;
- возможность уложить подготовку и результаты в лимиты runner;
- наличие артефактов и правильную классификацию ошибок.

Переход с 100 000 на 1 000 000 не требует заранее доказанного ускорения. Он проверяет самостоятельную гипотезу о масштабируемости. Ошибка модели блокирует переход; медленный корректный расчёт остаётся допустимым результатом.

### 15.3. Бюджет вычислений

Сначала выполнить scale-screen с K = 10. По фактическим временам оценить стоимость основной кампании в runner-минутах. Опубликовать оценку до запуска scale-main.

Для части из 12 job по 60 минут формальный верхний предел составляет 720 runner-минут плюс подготовка и валидация. Три повторения могут потребовать до 2 160 runner-минут на часть. Это пределы настроек, а не прогноз длительности.

Основная H3 для двух больших размеров содержит 24 экземпляра × 3 runner_round × 6 вызовов = 432 измеряемых процесса. При лимите 300 секунд их суммарная верхняя граница — 36 runner-часов для одной конфигурации GRID и одного выходного профиля. Верхняя граница 72 benchmark job по 60 минут — 72 runner-часа; генерация и отдельная валидация учитываются сверх этого. BURST, FULL, K=1000, ранжирование и альтернативные алгоритмы имеют собственные бюджеты. Увеличение числа эталонов не скрывается в прежней оценке четырёх вызовов.

Дробить кампанию по заранее сформированному списку точек. Не удалять медленные конфигурации из списка обязательных результатов. При исчерпании выделенного бюджета обозначить оставшиеся точки NOT_RUN и ограничить область выводов завершённой частью.

Стандартные runner публичных репозиториев и квоты закрытых репозиториев различаются [S10]. Публичность кода не менять ради вычислительного бюджета без отдельного решения владельца.

## 17. Пакет непосредственного сравнения с PlantTwin и BFG

Подготовить после E1 и первой завершённой большой серии:

- ограниченный набор на 10 000 операций для проверки импорта и правил;
- основной набор на 1 млн операций;
- готовые расписания и сценарии отказов;
- описание семантики из раздела 4;
- требуемый выход и единицы;
- правила времени, CPU, памяти и прекращения расчёта;
- образец заполнения результата.

Предлагать поставщикам две самостоятельные задачи:

| Задача | Общие входы | Общий результат |
|---|---|---|
| Проверка исполнения | Готовое расписание и внешние воздействия | Выпуск, сроки, срыв задания, время серии |
| Построение расписания | Операции, альтернативы, ограничения, целевая функция и бюджет поиска | Допустимость, качество плана и время построения |

Основной протокол Sheaft охватывает первую задачу. Для второй потребуется отдельная постановка планирования и реализация поиска расписания; её время не подменяется временем проверки.

Если продукт автоматически перепланирует работу, зафиксировать это как другой режим и включить такое же правило в сравнение. Если отключение перепланирования невозможно, точку считать функционально несопоставимой с основной серией.

Для экспериментальной модели на Amalgama Platform запросить доступ к библиотекам и условия использования. Документация предусматривает получение доступа к репозиторию библиотек по обращению [S6]. Подготовка модели на платформе не равнозначна испытанию готового PlantTwin.

Запуск коммерческого ПО также должен пройти через GitHub Actions. Если лицензия или архитектура продукта исключают такой запуск, непосредственное сравнение отложить и раскрыть ограничение. Использование внешней машины для обхода принятого режима исполнения в этот план не входит.

## 18. Возможные результаты и дальнейшие решения

| Результат | Решение |
|---|---|
| TSFG-OP не прошёл E0-core или E1 | Исправить семантику и повторить проверку. Приостановить заявления о производственной корректности |
| TSFG-OP корректен, но проиграл DES и DAG | Опубликовать измерения; исследовать стоимость обхода состояния и временного шага |
| Ускорение появилось только при агрегации F1 | Ограничить позиционирование однородными потоками и раскрыть класс точности |
| Агрегация пропустила срывы отдельных заказов | Использовать более подробное состояние либо ограничить выход агрегированной модели показателями, которые она воспроизводит |
| Ускорение исчезло на SPARSE | Указать зависимость от плотности событий; отдельно исследовать пропуск неизменных интервалов |
| Миллион операций превысил память | Опубликовать достигнутый предел и расход памяти; менять представление данных отдельной версией |
| Найденный резерв не улучшил результат | Проверить цепочку ограничений и критерий ранжирования; не объявлять ресурс причиной итогового срыва только по высокой загрузке |
| Ускорение и прикладной эффект устойчиво воспроизведены | Подготовить ограниченный ретроспективный пилот на данных предприятия |

Ретроспективный промышленный пилот потребует маршрута, плановых параметров, фактических событий исполнения и остановок за один согласованный период. Для него отдельно оценить полноту входов и воспроизведение фактических сроков. Синтетические отказы из этого протокола не заменяют статистику конкретного оборудования.

## 19. Формулировки для отчёта

При успешном пооперационном сравнении:

> На наборе из 1 млн индивидуальных производственных операций TSFG-OP проверил K сценариев за T секунд. При одинаковых правилах исполнения и лимитах ресурсов парное ускорение относительно DES-REF составило S. Указаны версии реализаций, класс точности и результаты повторений в GitHub Actions.

При успешной агрегации:

> Агрегированный профиль обработал задание с 1 млн исходных операций, представленное V состояниями. Время составило T; максимальные ошибки срока и выпуска составили соответствующие измеренные значения. Поддерживаемый состав результатов указан отдельно.

Для связи с конкурентами:

> Эксперимент подтвердил вычислительное преимущество относительно указанного событийного эталона в описанной области задач. Результат обосновывает проверку гипотезы о преимуществе при массовом анализе расписаний в сравнении с PlantTwin и BFG. Непосредственное сравнение продуктов не проведено.

Утверждение «быстрее BFG в S раз» допустимо только по непосредственному сопоставимому измерению. Опубликованные 45 минут не служат знаменателем для времени проверки готового плана.
