# Переиспользование исходного TSFG

Версия профиля: 1.2. Это дополнение имеет приоритет над описанием самостоятельного
C++ TSFG-GRID в протоколе 1.1. Семантика операций и критерии E0/Mk01 сохраняются.

Исходник S1: `a-a-k/ozone-tech_mb3r_lab_1084`, commit
`8510baf28673758f1e437d2dbc5a51ead9843a3b`. Репозиторий закрытый. Actions получает
его отдельным ключом deploy key с доступом только на чтение. Исходники и собранный
из них исполняемый файл не включаются в публичные артефакты. Для воспроизведения
этого участника нужен доступ к исходному репозиторию; DES/DAG остаются открытыми.

## Что именно исполняется повторно

`engines/tsfg_op/operation_adapter.go` добавляется в исходный Go package main.
Исходные файлы не изменяются. Вызывается существующая функция
`runGraphLocalTemporalCapacityModelWithRuntimeAndSink`; она строит граф и исполняет
`runGraphLinearTemporalCapacityModelWithRuntimeAndSink` из `graph_flow.go`.
Используются существующие `graphFlowSink` и `graphFlowNodeCoupler`, расчёт доступной
мощности, ограничение обслуживания объёмом работы, очереди узлов и общий шаг времени.
Собственные регрессионные тесты исходного Go-пакета выполняются перед E0.

Каждому станку соответствует узел. В его очередь через `PullNodeInput` поступает
остаток работы одной текущей операции. Мощность равна одной единице работы на
один tick времени; multiplier равен 0 при отказе и 1 при доступности. Обслуженный
объём возвращается через `RouteNodeOutput`. Именно исходное ядро, а не адаптер,
вычисляет этот объём. Адаптер проверяет целочисленность возвращённого значения.

Техническая линейная цепочка с нулевой пропускной способностью рёбер и пустым
конечным узлом удовлетворяет интерфейсу исходного графа. Между станками по ней
ничего не перемещается. Технологические зависимости задаются отдельными связями
операций в адаптере. Это кодировка независимых серверов в существующем ядре,
а не заявление о поддержке исходным агрегированным профилем индивидуальных заказов.

## Добавляемая семантика

На `BeginStep(t)` адаптер обновляет доступность и допускает только готовую голову
фиксированной очереди. Остальная очередь не обходится. `RouteNodeOutput` сохраняет
обслуженный объём. На `EndStep` все завершения фиксируются одним пакетом, после чего
обновляются непосредственно зависимые операции. Следующая граница допускает новые
начала. Отказ сохраняет текущую операцию и её необработанную работу в исходном узле.
Граница H обрабатывается также при остановке, включая допустимые начала ровно в H.

Внутренняя единица исходного ядра переобозначена как один целый tick эксперимента
(0,01 единицы Mk01); Δ=5 ticks. Поэтому ограничение исходного `graphFlowQuantum`
снизу в 0,1 внутренней единицы не меняет требуемую сетку. Все входные границы и
работа кратны Δ; последний шаг MISSION может быть короче Δ. Float64 в исходном ядре
представляет используемые целые точно; нецелое обслуживание считается ошибкой.

Полный обход индивидуальных операций на каждом шаге отсутствует. Однако исходное
ядро сохраняет свои обходы узлов/рёбер, выделения памяти и агрегированные метрики.
Его стоимость измеряется целиком. Пропуска пустых интервалов и календаря завершений
в этом профиле нет. Вычислительное преимущество не предполагается заранее.

## Участники и происхождение результатов

- `tsfg`: исходное Go-ядро S1 + новый адаптер фиксированных операций (основной TSFG).
- `des`, `dag`: независимые C++ реализации.
- `simpy`: независимый небольшой пооперационный oracle.
- `grid`: ранее написанная самостоятельная C++ реконструкция; оставлена только
  как вспомогательный контроль. Её результаты не обозначаются результатами S1.

Основной участник написан на Go, эталоны DES/DAG — на C++. Первый результат
проверяет корректность, поэтому различие языков не мешает его приёмке. Будущие
замеры смогут характеризовать конкретные реализации целиком; приписывать разницу
времени только алгоритму без дополнительного контроля языка и среды нельзя.

Прежний успешный E0 для `grid/des/dag/simpy` не является приёмкой `tsfg`.
После подключения исходного ядра весь E0 и Mk01 выполняются заново.
